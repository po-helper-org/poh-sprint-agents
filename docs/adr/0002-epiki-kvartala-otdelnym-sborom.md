# Эпики квартала добираем отдельным сбором, а не правкой сборщика спринта

Снимок спринта (`sprint-report.data.json`) содержит только эпики, по которым в спринте есть задачи: на момент решения в нём была меньше половины инициатив квартала, а у команды, только начавшей квартальные эпики, — почти ни одной. Отчёту о рисках нужны все, потому что инициатива, по которой никто не работает, — главный риск не дойти. Мы не меняем базовый сборщик: он под строгим замком (хеш кода в `sprint-report.lock.json`, после правки — `validate` и `lock` по трём командам), а лишние эпики без задач спринта изменили бы отчёт PO и колоду. Вместо этого `quarter.py fetch` читает список инициатив из кэша целей и сам забирает по ним из Jira только нужное (метаданные эпика, задачи эпика с датами и последней сменой статуса) тем же REST-транспортом только на чтение, что у `/sprint-blockers`, в свой файл `quarter-risks.data.json`.

## Consequences

- Два запроса в Jira на одни и те же эпики в одно утро (сборщик спринта и сбор квартала) — около минуты лишнего, зато замок и форма снимка не трогаются.
- Правила раскладки статусов по бакетам берутся из тех же `params` команды, что у сборщика, — «в ожидании» в обоих отчётах значит одно и то же.
