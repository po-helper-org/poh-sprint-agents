# БФТ — Встроенный коннектор к корпоративной JIRA (poh-sprint-agents, срез 2а)

> Бизнес-функциональные требования на срез «коннектор чтения JIRA внутри
> sprint-agent». Формат — тот же, что у [БФТ среза 1](bft-sprint-planner-slice1.md):
> БТ / ПТ / ФТ / НФТ / границы / трассировка. Демо-сценарий —
> [HOWTODEMO-jira.md](HOWTODEMO-jira.md).

**Статус:** реализовано (`plugins/dsh-plugin-sprint`). **Предмет:** раздел
«Управление спринтами» для DeepSeek Harness.

---

## 0. Контекст (As-Is → Gap → To-Be)

**As-Is.** Данные спринта живут в корпоративной JIRA, а sprint-agent работает с
волтом. Единственный путь трекера в чат — MCP-мост, и в харнессе он работает
плохо: инструменты подхватываются неустойчиво, отказы приходят без причины
(«не получилось» вместо «токен не принят»), доступы задаются файлом конфигурации
моста мимо интерфейса харнесса.

**Gap.** Нет пути «спросил в чате — получил данные из своей JIRA», в котором
доступы задаются в интерфейсе, проверяются до первого вопроса, а отказ называет
причину.

**To-Be.** Коннектор внутри самого раздела: карточка доступов в «Настройки →
Плагины», кнопка проверки подключения и нативные инструменты модели. Посредника
между моделью и трекером нет.

## 1. Бизнес-требования (БТ)

| ID | Требование | Источник |
|---|---|---|
| **БТ-JC-1** | Данные спринта доступны в чате **без MCP-моста** — прямым коннектором раздела | Задача: «DeepSeek Harness очень плохо работает с JIRA MCP» |
| **БТ-JC-2** | Доступы к корпоративной JIRA задаются **в интерфейсе харнесса**, не файлом конфигурации | HowToDemo, шаги 3–5 |
| **БТ-JC-3** | Рабочее подключение **проверяется до чата**, одной кнопкой, с понятным статусом | HowToDemo, шаг 6 |
| **БТ-JC-4** | Ответ модели опирается на **данные трекера**, а не на память: ноль выдуманных ключей, статусов и оценок | VISION, принцип «каждый факт ← источник» |
| **БТ-JC-5** | Срез **ничего не пишет** в трекер: обратимость среза 1 не нарушена | VISION, «обратимость первой»; НФТ-SP-2 |

## 2. Пользовательские требования (ПТ)

| ID | Роль | Требование |
|---|---|---|
| **ПТ-JC-1** | PO | Ввожу ссылку, токен и промт подключения в настройках раздела и вижу статус подключения сразу |
| **ПТ-JC-2** | PO | Спрашиваю в чате «покажи актуальные истории команды» — получаю истории своего проекта из JIRA |
| **ПТ-JC-3** | PO | Вижу причину отказа («токен не принят», «страница входа SSO»), а не «не получилось» |
| **ПТ-JC-4** | Скрам-мастер | Уточняю по исполнителю, статусу, конкретной задаче — тем же коннектором, без переключения инструмента |
| **ПТ-JC-5** | Владелец контура | Описываю свою JIRA своими словами (промт подключения) — модель учитывает это без правки кода |

## 3. Функциональные требования (ФТ)

| ID | Что делает | Где |
|---|---|---|
| **ФТ-JC-1** | Карточка «Управление спринтами» в «Настройки → Плагины», ключ пространства `sprint-management` | `src/client/index.tsx` |
| **ФТ-JC-2** | Полоса коннекторов: иконка JIRA раскрывает поля коннектора; полоса рассчитана на следующий источник | `src/client/SprintSettingsCard.tsx` |
| **ФТ-JC-3** | Поля: ссылка, токен, промт подключения; необязательные — проект, JQL историй, учётная запись Cloud, поле оценки | `src/settings.ts` |
| **ФТ-JC-4** | «Протестировать»: `/myself` + контрольный запрос историй по **введённым** значениям (сохранение не требуется); статус строкой | `src/connector.ts`, `src/channel.ts` |
| **ФТ-JC-5** | Инструменты модели `jira_current_stories`, `jira_search`, `jira_issue` — регистрация в `ctx.tools`, схемы уезжают в промт сами | `src/tools.ts` |
| **ФТ-JC-6** | Секция системного промта: контур, проект, когда звать инструменты, промт подключения владельца; не настроен — секция пуста | `src/prompt.ts` |
| **ФТ-JC-7** | Запрос историй: `project = КЛЮЧ AND sprint in openSprints()` либо свой JQL; фильтры инструмента дописываются перед `ORDER BY` | `src/jira/jql.ts` |
| **ФТ-JC-8** | Разбор ответа Server/DC и Cloud одним нормализатором: спринт в обеих формах, оценка из найденного поля, описание из строки и из ADF | `src/jira/normalize.ts` |
| **ФТ-JC-9** | Отказы названы по классам: `not-configured`, `bad-config`, `auth`, `query`, `not-json`, `timeout`, `network`, `http` | `src/errors.ts`, `src/jira/client.ts` |

## 4. Нефункциональные требования (НФТ)

| ID | Требование | Метрика |
|---|---|---|
| **НФТ-JC-1** | Без посредника | 0 процессов между моделью и JIRA; инструменты зарегистрированы в реестре харнесса |
| **НФТ-JC-2** | Ноль выдумок | Поля, которых нет в ответе JIRA, отсутствуют в результате и печатаются прочерком; проверено тестами |
| **НФТ-JC-3** | Одна дверь | Кнопка проверки и инструменты используют один код похода в JIRA (`SprintConnector`) — «зелёная» проверка означает работающий чат |
| **НФТ-JC-4** | Названный отказ | 100% отказов несут причину и HTTP-код, где он есть; HTML-ответ распознаётся как страница входа SSO |
| **НФТ-JC-5** | Обратимость | 0 запросов записи: только `GET`/`POST /search` — чтение |
| **НФТ-JC-6** | Настройка без перезапуска | Правка карточки действует со следующего вызова инструмента (настройки читаются на вызов, текст секции промта — провайдер) |
| **НФТ-JC-7** | Секретам не место в репозитории | Токен — в документе настроек либо в `JIRA_TOKEN` окружения; в `cordis.patch.yml` только бюджеты и потолки |
| **НФТ-JC-8** | Проверяемость | `npm test` — 61 тест, без сети и без живой JIRA (сетевой порт подменяется) |

## 5. Границы среза

**ВНУТРИ:** чтение JIRA (истории спринта, поиск по JQL, одна задача), карточка
доступов, проверка подключения, секция промта, промт подключения владельца.

**СНАРУЖИ:** любая запись в JIRA (заведение задач, статусы, комментарии,
материализация ПЛАНа — срез 2 дорожной карты), Confluence и другие источники,
карта KR↔эпик, мультиарендность (раздел живёт на машине владельца).
