# Эталонная колода отчёта — принципы формирования и разделения

> Источник: рабочая HTML-презентация спринта, 10 слайдов (вторая, полная
> редакция: добавлены слайд РИСКИ, третья карточка метрик, строки ACTIVITY).
> Это **эталон визуала
> и содержания**: к нему навык `sprint-result` приводит любой входящий контекст.
> Заменяет чёрно-белый документ-макет (решение О8 пересмотрено, см. §9).
>
> Материал обезличен: сняты ФИО, названия систем, вендоров и внутренних
> сервисов. Примеры ниже синтетические.

---

## 1. Форма: колода, а не документ

Страница — **лента слайдов** шириной 1280 на сером фоне с тенью. Слайд несёт
номер в правом нижнем углу; отчёт открывают на большом экране и листают на
ревью.

Важная деталь геометрии: `min-height:720px`, а не `height`. **720 пикселей —
минимум, не потолок.** Слайд растёт под содержание: самый плотный стрим
эталона несёт восемь строк на одном слайде и никуда не режется. Значит разрез
стрима — решение автора, а не механика формата.

Типографика — Arial, не гарнитура документа. Заголовок слайда 30px, обычным
начертанием, не жирным. Титул и HERO — 52px и 46px. Текст таблицы 12.5px.

---

## 2. Разделение: два уровня, команда → стрим

Колода делится дважды.

**Уровень 1 — команда.** HERO-слайд: короткая чёрная черта 64×3, название
команды крупно (46px), под ней одна строка с перечнем стримов этой команды.
Содержания на слайде нет, он только режет ленту и объявляет владельца
следующих слайдов.

**Уровень 2 — стрим.** Слайд с таблицей. Заголовок = название стрима,
подзаголовок = `Спринт {sprint} · стрим "{название}"`. **Один стрим — один
слайд, сколько бы в нём ни было строк.**

Стрим — то же, что инициатива и OBJ-срез квартала (решение О1). Новое — уровень
команды над ним.

### Что именно даёт разделение команд

Команды в эталоне **не равновелики**: у одной один стрим, у другой три. Деление
идёт не «поровну», а по владельцу работы.

| Где | Как отражена команда |
|---|---|
| Титул | надзаголовок — вся единица целиком: `Команда "{A}/{B}"` |
| HERO | `{ИМЯ} команда` + строка стримов этой команды |
| Слайды стримов | команда не повторяется: её объявил HERO |
| Метрики | **слайд принадлежит одной команде**: `Метрики {ИМЯ} команды`. Метрики второй команды в колоде нет |
| Итоги | общие: подзаголовок `{N} инициатив по {M} стримам · {A} + {B}` |
| РИСКИ | общие, команда не указана |

Отсюда правило: **стримы и метрики — по командам, итоги и риски — общие.**
Метрики привязаны к команде потому, что velocity и burndown считаются на
команду, а не на отчёт.

Одна команда → HERO-слайды не нужны, стримы идут сразу после титула.

---

## 3. Порядок колоды

```
1  Титул          надзаголовок «Команда {A}/{B}», ФАКТ {sprint}, ответственный
2  HERO           команда A + перечень её стримов
3..n               слайд на каждый стрим команды A
   HERO           команда B
   …               слайд на каждый стрим команды B
   Метрики        «Метрики {B} команды», 2–3 карточки с графиками
   Итоги          три счётчика + ключевые риски и блокеры этого спринта
   РИСКИ          квартальные риски блоками — последний слайд
```

Итог **в конце, а не в начале**. Колоду читают линейно и вслух: сначала
показывают работу, потом сводят. Это отличается от документа, где резюме
ставят первым, — и это осознанная особенность формы.

---

## 4. Слайд стрима

```
{Название стрима}                              [легенда: 3 пилюли]
Спринт {sprint} · стрим "{название}"

| Задачи (26%) | Комментарий (58%) | Результат (16%) |
…
Сортировка: по убыванию результата
                                                            {номер}
```

**Легенда** повторяется на каждом слайде стрима в правом верхнем углу: три
пилюли с заливками и подписями «выполнено-100%», «в работе сделано от 50% до
99%», «в работе сделано до 50%». Она объясняет заливку строк.

**Три колонки, ширины фиксированы.** Колонки OKR в эталоне нет: трассировка к
цели живёт в названии стрима, а не в ячейке. Ширина комментария вдвое больше
задачи — комментарий и есть содержание отчёта.

---

## 5. Заливка — строка целиком, не ячейка

Статус красит **всю строку**, а не ячейку результата. Слайд читается как
светофор: взгляд сверху вниз по цветным полосам, а не по колонке с числами.

| Класс | Значение | Заливка строки | Пилюля легенды |
|---|---|---|---|
| зелёный | `100%` | `#D9EAD3` | `#B6D7A8` |
| жёлтый | `50–99%` | `#FFF2CC` | `#FFE599` |
| красный | `0–49%` | `#FDE9E9` | `#F4CCCC` |

Граница жёлтого включает 50: `50%` — жёлтая строка, `40%` — красная.

**Стоп-маркеры в колонке результата** отделяют два разных нуля:

- `🛑 0%` — держит внешняя зависимость: смежная команда не отдала, поставщик
  перенёс, работа не начиналась не по решению команды;
- `🚫 0%` — сняли сами: исполнителя переключили, приоритет сменили.

Разница не косметическая. Первое — вопрос к смежникам, второе — решение,
которое команда объясняет сама.

## 6. Как пишется текст

### Название задачи

**Ни роли, ни исполнителя.** В эталоне нет ни одного `[BE]`, ни одной фамилии:
`Переключение 50/50`, `Убрать задержку уведомлений`, `Спонсорские промокоды`.
Отчёт про работу, не про людей.

Два способа назвать:
- **именная группа** — «Отладка задержки синхронизации», «Декомпозиция
  миграции хранилища»;
- **стрелка потока данных** — «Поставщик → процессинг», «Каталог → шина →
  витрина». Стрелкой называют интеграции: она сама показывает, что куда едет.

Глагол в названии — только когда работа снимает проблему: «Убрать задержку».

### Ячейка «Комментарий»

```
• факт
• факт
След. шаг: что делаем дальше
```

Маркированный список без меток вроде «Образ результата» или «Факт». Одна
мысль — один пункт. Внутри пункта допустим жирный ярлык, когда пункт отвечает
на отдельный вопрос: `**Статус интеграции:** не работает, ждём логи`.

**Строка следующего шага** — отдельная от списка, ярлык жирный, значение
обычным. Ярлык варьируется по горизонту: `След. шаг:`, `Следующий спринт:`,
`В следующем спринте:`.

### Логика комментария — четыре слота

Замеры по черновой колоде (`.pptx`, 227 ячеек, 306 строк) показывают устойчивую
композицию. Ячейка — не абзац, а последовательность слотов в фиксированном
порядке:

| Слот | Ярлык | Частота в источнике |
|---|---|---|
| обещание из ПЛАН | `Образ результата:` | 43 — самый частый ярлык |
| факт | без ярлыка, пунктами | в каждой ячейке |
| почему не 100% | `Причина:` · `Блокатор:` · `Открытый вопрос к {кому}:` | 3 + 4 + единично |
| что дальше | `След. шаг:` · `Следующий спринт:` | 9 |

Причина и следующий шаг встречаются **реже, чем строк, которым они нужны** —
это главный дефект источника, и ровно его закрывает гейт 2.

Бюджет длины по тому же замеру: медиана строки — **8 слов**, 61% строк ≤ 12,
три четверти ≤ 19, максимум 54. Строка на 54 слова со слайда не читается: её
проматывают глазами и слушают докладчика.

Полные правила — `resources/comment_logic.md`.

### Регистр

- **Дата вместо «скоро».** «11 сентября — статистика», «8 сентября откатили»,
  «до 22 сент — релиз». Дат в эталоне больше, чем оценочных слов.
- **Расписание в следующем шаге через `;`**: «11 сент — завершить разработку;
  14 сент — в тест; до 22 сент — релиз в прод».
- **Время глагола несёт статус.** Прошедшее — сделано («переключили»,
  «откатили»), настоящее — идёт сейчас («отлаживаем», «решаем проблемы с
  DBA»). Будущего нет: будущее живёт в строке следующего шага.
- **Причина — факт без оправдания.** «Исполнитель был переключён на отладку»,
  «Смежная команда перенесла работы на следующий квартал». Ни «к сожалению», ни «не
  успели».
- **Отдельный тип пункта — открытый вопрос:** «Открытый вопрос к {кому}: зачем
  усложнять цепочку, если сейчас и так работает». Вопрос адресован поимённо и
  живёт в отчёте до ответа.
- **Оценка качества допустима, если она факт:** «Качество разработки низкое».
  Это вывод спринта, а не эпитет.

Чего в тексте нет: вводных, связок, «мы планируем», «в рамках», «удалось»,
восклицаний и любых слов, которые можно убрать без потери факта.

### Расхождение эталона с гейтом 2

Две строки на `0%` идут **без следующего шага** — в них есть причина и открытый
вопрос, но не сказано, что происходит дальше. Гейт 2 навыка на таких строках
сработает. Расхождение оставлено намеренно: это ровно тот случай, ради которого
гейт заводился.

## 7. Сортировка по убыванию результата

Строки внутри стрима отсортированы **по убыванию процента**, и на слайде стоит
явная подпись «Сортировка: по убыванию результата».

Порядок из плана не наследуется. Наверху закрытое, внизу заблокированное:
докладчик проходит слайд от достигнутого к проблемному, и разговор упирается в
блокеры в конце, а не в начале.

Подпись обязательна. Без неё читатель принимает порядок за приоритет.

## 8. Служебные слайды

**Метрики.** Слайд принадлежит одной команде: `Метрики {ИМЯ} команды`.
Карточки в ряд по две; при трёх карточках третья занимает ряд целиком
(`.metrics-grid.tri`). Заголовок метрики, картинка во всю ширину карточки,
**необязательный** абзац-объяснение под ней: в полной редакции эталона у
карточек объяснений нет вовсе, в ранней — есть. Объяснение говорит, что
изменилось и почему, и не пересказывает график цифрами.

**Итоги.** Три счётчика в ряд — «завершено на 100%», «в работе 50–99%»,
«до 50% / заблокировано» — крупным числом на заливке своего цвета. Под ними
блок «Ключевые риски и блокеры»: список, где имя блокера выделено жирным, а за
ним одной строкой суть и срок.

Счётчики считают **строки**, а не SP (решение Д1), и покрывают все стримы всех
команд. Подзаголовок: `{N} инициатив по {M} стримам · {A} + {B}`.

Тонкость: `{N}` считает **все** строки, включая `ACTIVITY`, а три счётчика —
только те, что стоят на шкале. В эталоне 19 инициатив при счётчиках 3 + 10 + 4
= 17: две строки `ACTIVITY` в счётчики не идут, но из отчёта не пропадают.

**РИСКИ.** Отдельный последний слайд, подзаголовок «Срыв OKR-коммитментов и
внешние зависимости». Блоки с красной левой чертой: заголовок риска и абзац
прозой.

Это **не то же самое**, что «Ключевые риски и блокеры» на слайде итогов. Там —
тактика этого спринта, одна строка на блокер, имя блокера жирным. Здесь — что
ставит под удар квартал: сорванный коммитмент OKR, взаимная блокировка со
смежной командой, операционная зависимость. Горизонт разный, поэтому и слайды
разные.

## 9. Что меняется в навыке против решения О8

| Было (документ-макет) | Стало (эталон) |
|---|---|
| прокручиваемый документ, колонка 860px | лента слайдов 1280×720 |
| Georgia, чёрно-белая типографика | Arial, палитра статусов |
| заливка только ячейки результата | заливка строки целиком |
| комментарий помеченными строками | маркированный список + строка следующего шага |
| 4 колонки, включая OKR | 3 колонки |
| один уровень: инициатива | два уровня: команда → стрим |
| порядок строк из плана | сортировка по убыванию результата |
| итог первым блоком | итоги последним слайдом |
| ступень лестницы в ячейке результата | ступени в ячейке нет |
| исполнитель ролью в названии задачи | ни роли, ни исполнителя |
| один слайд метрик на отчёт | слайд метрик на команду |
| риски одним списком на итогах | тактические на итогах + квартальные отдельным слайдом |

Две строки требуют решения PO:

- **Ступень лестницы** (решение О2): в эталоне ячейка результата несёт только
  число. Вывод никуда не девается, вопрос в том, где его показывать — см. Д4.
- **Исполнитель** (решение Д3: «ролью»): в эталоне его нет ни в одной строке.
  Навык оставил префикс необязательным — рендерится, если есть, но эталон
  отчёта написан без него. См. Д5.

Цикл правок (комментарии на странице → промт) в эталоне отсутствует: это
инструмент навыка, а не часть отчёта. Он сохраняется, но убран в поля и не
печатается — на слайдах его не видно.
