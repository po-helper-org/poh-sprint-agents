# `/actual-sprint` — отчёт по факту спринта

Навык собирает одну самодостаточную HTML-страницу: что происходит в текущем спринте, как команда шла последние три спринта и кто что делал за неделю. Только чтение — в JIRA ничего не пишет.

Данные берутся **только** из детерминированных сборщиков: ИИ пишет и проверяет их код, но сам данные отчёта не собирает. Поэтому отчёт воспроизводим, а чем и когда собрана каждая команда, runner печатает в сводке и кладёт в `_meta` данных.

Страница одна на все команды: переключатель вкладок в шапке, у каждой команды своя доска, свой спринт и своя корзина заметок.

---

## Быстрый старт

```bash
bash install.sh                 # развернуть навыки и runner в проект
export JIRA_URL=https://jira.example.com
export JIRA_PERSONAL_TOKEN=…    # личный токен; в файлы он не пишется никогда
```

Дальше в Claude Code:

```
/sprint-setup                   # один раз: конфиг с командами и досками
/collector-validate team-a      # один раз на команду: сверка с JIRA и фиксация
/actual-sprint                  # каждый раз: собрать отчёт
```

Перед первым походом в JIRA полезно проверить стенд — он смотрит только локальные вещи и в сеть не ходит:

```bash
python3 .claude/skills/actual-sprint/runner/run.py doctor
```

```
python         ✓ 3.11.15
плагин         ✓ 1.0.0, контракт и шаблоны на месте
конфиг         ✓ sprint-report.config.toml, команд 2, strict вкл
адрес JIRA     ✓ JIRA_URL задан
токен          ✓ JIRA_PERSONAL_TOKEN задан
ca_bundle      — не задан (нужен, только если инстанс за корпоративным CA)
[team-a] ✓ base, проверен 2026-09-28
[team-b] ✓ collectors/team-b, проверен 2026-09-28

Стенд готов. Первый поход в JIRA — python3 run.py validate <slug> --sample 5
```

Что делать, когда что-то пошло не так на живом инстансе — **[отладка](actual-sprint-debug.md)**: таблица «сообщение → причина → действие», снятие сырых ответов трекера и что из этого можно показывать наружу.

Открывать страницу лучше через локальный сервер, а не двойным кликом:

```bash
python3 -m http.server 8777 --directory reports
# http://127.0.0.1:8777/sprint-report.html
```

Почему не `file://` — заметки хранятся в `localStorage`, а он привязан к origin. У `file://` origin непредсказуем, и корзина может не сохраниться между открытиями.

## Кто собирает данные

Данные собирает **сборщик** — отдельная программа на команду. Модель его пишет, чинит и проверяет, но никогда не собирает данные сама: ни одно число на странице не получено ИИ напрямую из трекера. Между ними контракт:

| Кусок | Где | Зачем |
|---|---|---|
| Схема объекта команды | `contract/team.schema.json` | что должно быть в данных, до последнего поля |
| Протокол сборщика | `contract/PROTOCOL.md` | как запускается, что на входе и выходе, коды выхода |
| Правила бакетов | `contract/status_rules.json` | раскладка статусов по шести бакетам, данными а не кодом |
| Runner | `runner/run.py` | единственный способ собрать отчёт |
| Базовый сборщик | `templates/python/collector.py` | все правила команды вынесены в `params` |

Отчёт собирается одной командой:

```bash
python3 .claude/skills/actual-sprint/runner/run.py run --config sprint-report.config.toml
```

```
[team-a] base@1.0.0                  ✓ проверен 2026-09-28
[team-a] доска «Scrum Board Платформа» (#101), спринт «Спринт 74» | эпиков 7 | закрыто 18/41 | событий 63 | 11 запросов | 14.2s
[team-b] collectors/team-b  sha 9b01e4d ✓ проверен 2026-09-28
[team-b] доска «Scrum Board Мобильное» (#202), спринт «B-19» | эпиков 4 | закрыто 9/22 | событий 31 | 9 запросов | 6.8s
схема ✓   инварианты 24/24 ✓   предупреждений 1   заметок подхвачено 5
→ reports/sprint-report.html
```

## Подключить новую команду

1. **Конфиг.** `/sprint-setup` задаёт вопросы по одному и пишет `sprint-report.config.toml`. Токен в файл не попадает — только имя переменной окружения.

   ```toml
   [[teams]]
   slug  = "team-a"
   name  = "Команда A"
   board = 101
   collector = "base"
   [teams.params]
   story_types  = ["История", "История Enabler", "Story"]
   sprints_back = 3
   [teams.params.status_buckets]
   "Ожидает релиза" = "review"
   ```

2. **Свой сборщик — только если нужен.** Различаются типы задач, статусы, поле эпика, глубина по спринтам? Это `params`, кода писать не надо. Отличается сам алгоритм (несколько досок, свой источник спринта) — тогда `/collector-new team-b`: команда копирует шаблон в `collectors/team-b/`, правишь точки `# TEAM RULE:`.

   ```toml
   [teams.collector]
   cmd     = ["python3", "collector.py"]
   cwd     = "./collectors/team-b"
   timeout = 300
   ```

3. **Проверка.** `/collector-validate team-b`: runner прогоняет схему и 12 инвариантов, печатает выборку задач, ИИ сверяет её с JIRA поле за полем и показывает расхождения. После вашего «да» хеш сборщика пишется в `sprint-report.lock.json`.

4. **Дальше только `/actual-sprint`.** Если сборщик изменится хоть на байт, runner откажется его запускать и попросит перепроверку:

   ```
   [team-b] ✗ сборщик изменён после проверки (sha 9b01e4d → c77a210).
            Запустите /collector-validate team-b. HTML не сгенерирован.
   ```

Почему так строго: правило команды, которое никто не сверял с трекером, выглядит на странице точно так же, как сверенное. Хеш — способ отличить одно от другого.

## Что на странице

### Таблица эпиков

Единица отчёта — **эпик**, не история: PO трекает прогресс на этом уровне. Истории без эпика не выбрасываются, а собираются в псевдо-эпик «Без эпика».

В строке — счётчики статусов по всей иерархии (истории плюс подзадачи) в виде `2/2/3/0/5/1`. Порядок фиксирован, цвет на бакет:

| Цвет | Бакет |
|---|---|
| серый | Открыто |
| красный | Заблокировано |
| синий | В работе |
| жёлтый | Тестирование |
| оранжевый | Ревью |
| зелёный | Готово |

Подписей нет намеренно — расшифровка приходит подсказкой при наведении, только по ненулевым: «2 — в бэклоге, 5 — в ревью · всего 13».

Клик по строке открывает панель эпика со списком историй спринта. Кнопка **«Смотреть весь эпик»** в шапке панели показывает полный объём эпика — и то, что в спринте, и сделанное раньше, и бэклог: сверху «Сделано X из Y», ниже разделы «Осталось» (по процессу: заблокировано, в работе, тестирование, ревью, открыто) и «Сделано». При открытии всё свёрнуто — видны итог и заголовки со счётчиками; раздел и каждый статус внутри «Осталось» раскрываются по клику. У каждой задачи — метка «в спринте», имя прошлого спринта или «вне спринта». У эпика, истории и подзадачи — приоритет из JIRA: `⇈` критический/блокирующий, `↑` высокий, `=` средний, `↓` низкий, `⇊` самый низкий, `·` не задан; точное имя — по наведению. У каждой истории — статус, возраст статуса и инициалы исполнителя (полное имя по наведению). Стрелка разворачивает подзадачи. Правый клик по строке — заметка к ней.

**Возраст статуса** — сколько дней статус не менялся: «1д», «22д». Дольше трёх дней без движения — красным. Считается от даты из changelog, а не от `updated`: последнее двигается от любой правки, включая комментарий, и завышало бы свежесть. У закрытых задач возраст всегда зелёный — они стоят без движения по определению.

### Сводный отчёт за 3 спринта

Клик по Lead Time в шапке. Три графика:

**Burndown текущего спринта.** Серая прямая — идеальный темп, красная ломаная — фактический остаток, обрывается на сегодня. Объём пересчитывается по дням из changelog поля `Sprint`, поэтому внесённые и вынесенные посреди спринта задачи видны ступеньками. Если брать сегодняшний объём как стартовый, burndown врёт.

**Производительность.** Пара столбцов на спринт: плановый разложен по текущим статусам, рядом сделано. Видно, где именно осело незакрытое. Считаются задачи, а не story points — поле заполнено у 67–88% задач в зависимости от спринта, столбец в SP потерял бы до трети работы.

**Диаграммы управления** — отдельно по историям и подзадачам, у подзадач свой масштаб Cycle Time. По горизонтали дата закрытия, по вертикали Cycle Time. Красные точки — выбросы (`среднее + σ`), жёлтые — **зона риска**: задачи, которые ещё не закрыты, но уже идут дольше медианы. Это единственные точки, которые говорят о будущем: выбросы уже случились, а эти ещё можно вытащить. Под графиком оба списка кликабельны: строка — название, статус и дни в ровных колонках; правый клик — заметка к задаче.

Под графиками только легенда. Как читать график — в подсказке **«i»** у заголовка, там же статистика окна (медиана, среднее, σ). Правый клик по графику — заметка к графику целиком.

**Инсайды ИИ** — последний раздел сводного отчёта: на что обратить внимание PO и что можно сказать о состоянии команды в этом спринте и о тенденции за 3 спринта. Это 3–8 наблюдений по важности: уровень (нужна реакция / присмотреться / работает / наблюдение), к чему относится (спринт, команда, конкретный график), что видно в цифрах и что сделать; ключи задач — ссылками в JIRA. Правый клик по наблюдению — заметка к нему. Пока агент не смотрел этот сбор, раздел подсказывает: «Попросите его: /sprint-insights».

### Инсайды ИИ: отдельный конвейер

Отчёт собирается скриптом, без модели, — так цифры каждый раз одни и те же. Интерпретация — отдельный шаг, где работает агент:

1. `insights.py facts` — скрипт достаёт из снимка `reports/sprint-report.data.json` факты: по графикам (отставание от идеальной прямой, плато, добавленный объём, план против сделанного, выбросы и зона риска с отношением к медиане, тренд Cycle Time), по спринту сейчас (статусы, блокеры, задачи без движения) и по тенденции команды (пропускная способность, медианы Lead и Cycle Time по спринтам).
2. Агент пишет `reports/sprint-insights.json`: 3–8 наблюдений по важности, с уровнем, меткой «о чём» и действием; и бизнес-блок для презентации «ФАКТ | спринт» — Sprint Goal и OKR стримов (цели только из OKR/roadmap PO), причины и следующие шаги строк, изменения, демо, квартальные риски.
3. `insights.py apply` проверяет файл — форма, ключи задач только из данных команды, хеш данных совпадает, числа есть в фактах (иначе предупреждение) — и пересобирает страницу из снимка через `run.py render`, без JIRA.

Наблюдения привязаны к хешу данных команды. После нового `/actual-sprint` старые на страницу не попадут — runner напишет «инсайды устарели … — /sprint-insights». Навык: `.claude/skills/sprint-insights/SKILL.md`.

### Презентация «ФАКТ | спринт»

Кнопка **«Презентация»** справа вверху открывает второй отчёт из тех же данных — колоду «ФАКТ | спринт». Отчёт PO (страница) нужен для синхронизации с техлидами; колода — для управляющего комитета, PO смежных департаментов и бизнес-заказчиков: что каждая команда сделала за спринт и как это служит целям. Форма — эталонная отчётная колода спринта PO: лента белых слайдов 1280×720.

| Слайд | Что на нём | Откуда |
|---|---|---|
| Титул | «ФАКТ \| спринт», команды, период, статус, время данных | данные сбора |
| Разделитель команды | имя команды и её стримы | данные |
| Стримы | стрим = эпик, строка = история спринта: «Задачи \| Комментарий \| Результат», строка светофором; шапка стрима — OKR и Sprint Goal | результат и факты — данные; Sprint Goal, OKR, причины, след. шаги — бизнес-блок агента |
| Изменения в процессе спринта | было → стало → что вышло | объём спринта — burndown; договорённости — агент |
| Демо | что показываем руками | агент; нет — слайда нет |
| Метрики команды | burndown и производительность | данные; подпись — наблюдение агента |
| Итоги спринта | 100% / 50–99% / до 50%; блокеры по давности; что не закрыто | данные |
| РИСКИ | квартальные: коммитменты OKR, внешние зависимости | агент; нет — слайда нет |

**Результат строки.** Закрытая история — 100%. Иначе — большее из доли закрытых подзадач и стадии (в работе 30, тест 80, ревью 90, не начата 0), но не выше 90%. Заблокированная — 🛑, не начатая — 🚫. Строка: 100% — зелёная, 50–99% — жёлтая, ниже — красная. Как посчитано — в подсказке у процента. Мелкие стримы команды делят слайд — до восьми строк, у каждого своя шапка.

**Правки.** «Слайды» — оглавление. Клик по строке — правка к истории, выделение текста — правка к слайду с цитатой; правки ложатся в ту же корзину, что у отчёта PO, и уходят промтом для ИИ. В печати их нет: «PDF» — по слайду на страницу. Стрелки листают, Esc закрывает, адрес `#presentation` открывает сразу колоду.

Runner пишет рядом с отчётом `reports/sprint-business.html` — тот же отчёт, открытый сразу колодой и без выхода в отчёт PO. Его отправляют комитету; путь — ключ `business` в конфиге.

### Лента активности

Кнопка «Logs». Что команда делала за неделю: смены статусов, комментарии с цитатой и созданные задачи. Фильтры по типу события и по автору комбинируются.

Переходы вида `Backlog → Backlog` не прячутся: в JIRA это реальное событие workflow, и скрывать его — врать, что человек ничего не делал.

## Заметки: корзина справа вверху

Кнопка **«Комментарии (N)»** в правом верхнем углу раскрывает панель с заметками к спринту. Каждая заметка — строка текста; если она привязана к эпику или задаче, под текстом мелко написано `ключ · название`.

- **Новая заметка** — поле «Добавить заметку» сверху панели. Как только начали писать, под ним появляется «К чему» — ключ эпика или задачи, подсказки берутся из отчёта. Пусто — заметка без привязки: процесс, истории, которых нет в спринте, замечания к агенту и платформе. Ключ не из отчёта (история вне спринта) тоже подойдёт — сохранится как «Вне отчёта». Enter — добавить.
- **Заметка к строке** — правый клик по эпику в таблице, по истории или подзадаче в панели эпика, по событию в ленте «Logs». Поле появляется у курсора, уже привязанное к строке; над ним — заметки к той же сущности. Enter — сохранить, Shift+Enter — перенос строки, Esc — отмена.
- **Редактировать и удалить** — наведите на заметку: справа появятся карандаш и мусорка. Карандашом правится и текст, и привязка прямо в строке (Enter — сохранить, Esc — отмена). Когда заметка создана и изменена — в подсказке при наведении.
- **«Скопировать промт для ИИ»** — внизу панели; иконка-глаз рядом показывает сам текст. Сначала контекст (команда, спринт, доска, время данных JIRA), затем заметки строками `N. [к чему относится] текст`. В скобках — тип, ключ, название, эпик, приоритет, статус и исполнитель на момент записи: по ним LLM сразу понимает, о чём речь, даже когда отчёт уже пересобран.

Пример промта:

```
Заметки PO к отчёту спринта — учти их при разборе спринта и в ответах.
Команда «Платформа» · Спринт 74 · доска «Scrum Board Платформа» · данные JIRA на 15.09.2026 17:00.
Формат: номер. [к чему относится] текст заметки. [без привязки] — заметка о процессе в целом.

1. [без привязки] Истории по SEO нет в спринте — завести?
2. [Эпик INIT-111 «Единый каталог позиций» · приоритет Высокий] Ждём DBA
3. [История INIT-102 «Переезд на новое хранилище» · эпик INIT-101 «Приём заказов из внешнего канала» · приоритет Критический · статус В работе · исполнитель Участник Ж] Проверить, не блокирует ли релиз
4. [Вне отчёта SEO-77 «перелинковка»] Этой истории нет в спринте
```

У эпика с заметками кнопка «Статус» получает точку, у задачи — счётчик.

Корзина живёт в `localStorage` браузера, отдельно для каждой команды и спринта: новый спринт начинается с пустой корзины, прошлая остаётся в браузере. `localStorage` привязан к origin — открыли отчёт с другого порта или в другом браузере, и заметок там нет. Поэтому то, что нужно агенту, копируйте промтом в чат.

**Заметки прошлых версий.** Раньше у эпика была одна большая заметка и выгрузка `sprint-report-notes.json` кнопками «Заметки ⬇ / ⬆». Их больше нет. Заметки, оставшиеся в браузере или в файле рядом со страницей, при первом открытии переезжают в корзину с пометкой «из заметки» — ничего не теряется.

## На телефоне и как приложение (PWA)

Страница подстраивается под телефон (проверено на iPhone 15 Pro, 393 px, в обеих ориентациях):

- **Главный экран.** Строка эпика — карточка: название во всю ширину, под ним счётчики статусов и `›`; точка перед `›` — к эпику есть заметки. Вкладки команд — в одну строку, листаются пальцем.
- **Панель эпика, «Весь эпик», сводный отчёт, Logs** — на весь экран, крестик крупный и ниже «чёлки». У задачи статус и возраст — второй строкой под названием.
- **Заметка к строке — долгое нажатие** (полсекунды) на эпике, задаче, задаче-выбросе, графике или событии ленты: правой кнопки на телефоне нет, а Safari не шлёт её аналог. Поле открывается сверху, чтобы его не закрыла клавиатура; «Отмена» и «Сохранить» — кнопками.
- **«i» у графика — по тапу**, подсказка выезжает шторкой снизу; повторный тап или тап мимо закрывает.
- В корзине карандаш и мусорка видны всегда — наведения нет.

**Как поставить на экран «Домой».** Страница — один файл, иконка и всё нужное для режима приложения уже внутри. Добавить на экран «Домой» iOS даёт только странице, открытой в Safari **по ссылке** (http/https): HTML-файл из Telegram или «Файлов» откроется для чтения, но иконкой не станет. Положите `reports/sprint-report.html` туда, где его видно по ссылке во внутренней сети, — общий веб-сервер, статический хостинг или хотя бы `python3 -m http.server 8777 --directory reports` на машине с отчётом. Дальше в Safari: «Поделиться» → «На экран „Домой“». Открывается без панелей браузера, под именем «Спринт». Ссылки в JIRA уходят в Safari.

Режим офлайн страница не даёт: для него нужен service worker отдельным файлом, а отчёт — один файл. Заметки хранятся в браузере телефона — своя корзина на каждом устройстве; наружу их уносит «Скопировать промт для ИИ».

## Демо без доступа к трекеру

Показать навык или снять скриншоты можно без единого запроса в JIRA:

```bash
python3 .claude/skills/actual-sprint/scripts/demo_data.py --html demo-report.html
```

Собирает страницу на синтетических данных: три команды, вымышленные эпики, задачи `INIT-*`, люди «Участник А…». Сид фиксирован — одинаковый запуск даёт одинаковую картинку, скриншоты не «плывут» между пересборками. Корпоративных данных в файле нет по построению, а не по результату вычистки.

## Прогон без похода в JIRA (record / replay)

Сборщик умеет сохранять сырые ответы трекера и работать из них:

```bash
# записать ответы (нужен доступ к JIRA)
python3 .claude/skills/actual-sprint/runner/run.py validate team-a   # см. params.record
# прогнать сборщик по записанному, без сети
```

```toml
[teams.params]
record = "./fixtures/team-a"     # положить ответы
# replay = "./fixtures/team-a"   # работать из них
```

На replay стоят тесты репозитория и сверка после правки сборщика: одинаковые фикстуры и одинаковый `now` дают тот же JSON. Токен в дампы не попадает — сохраняются только путь запроса и тело ответа.

Если данные уже собраны, а поменять надо только вёрстку — сборщик на replay пересоберёт страницу из записанного, в трекер идти не нужно.

## Что считается и как

| Метрика | Определение |
|---|---|
| Lead Time | от создания задачи до перехода в финальный статус |
| Cycle Time | от первого взятия в работу до финального статуса |
| Возраст статуса | от последней смены статуса до сегодня |
| Зона риска | незакрытая задача, идущая дольше медианы Cycle Time своей группы |
| Выброс | закрытая задача с Cycle Time выше `среднее + σ` |

Разница медиан Lead и Cycle — время ожидания в очереди до взятия в работу.

Статусы раскладываются по шести бакетам эвристикой, выверенной регрессией по всем ~330 статусам инстанса. Готовность определяется категорией JIRA и точным совпадением имени, **не подстрокой**: подстрочный поиск уводил «Ожидает решения КЦ» и «Аналитика завершена» в «Готово». Подробности — `resources/status_mapping.md`.

## Если что-то не так

**«Сборщик не проверен» / «изменён после проверки».** Так работает `strict`: код, который никто не сверял с трекером, не запускается. `/collector-validate <slug>` — и снова можно собирать.

**«JIRA недоступна» (код 3).** Нет сети, VPN или токен просрочен. ИИ в этом случае не пойдёт собирать данные в обход — и не должен.

**Схема или инвариант упали.** Сборщик отдал не то, что обещал: сообщение называет команду и путь поля (`[team-b] metrics.overall.lead`). HTML не пишется, прошлый файл остаётся целым. Починка — в коде сборщика.

**Предупреждение «статус … не покрыт правилами бакетов».** В workflow появился статус, которого правила не знают, и он уехал в «В работе». Опишите его в `params.status_buckets` — или это сигнал, что процесс команды поменялся.

**Собрался не тот спринт.** Список спринтов доски пагинируется. У доски с длинной историей первая страница отдаёт спринты многолетней давности — сборщик обходит все страницы, но если правите его, не потеряйте пагинацию.

**Пустые метрики.** В changelog имена статусов приходят на языке workflow (`Closed`, `In progress`), а `/rest/api/2/status` отдаёт русские. Сопоставлять нужно по числовым id, иначе совпадений ноль.

**Задачи висят, запросы таймаутят.** Проверьте VPN: без него корпоративный хост резолвится в публичный адрес и всё виснет. Быстрая проверка — `curl -sk -m 10 $JIRA_URL/rest/api/2/myself`.

**Корзина пуста.** Открыли с другого порта или в другом браузере: заметки живут в `localStorage` этого origin. Нужное агенту копируйте промтом в чат сразу.

## Границы

Навык только читает JIRA и генерирует локальный файл. Не пишет в JIRA и Confluence, не публикует страницу наружу, не ходит по расписанию. Токен берётся из окружения и никуда, кроме JIRA, не отправляется. Проверка TLS включена всегда: корпоративный CA подключается через `jira.ca_bundle`, а не отключением проверки.

В этом срезе шаблон сборщика один — Python. Протокол языконезависим (вход stdin, выход stdout, коды выхода), поэтому сборщик можно написать на чём угодно; шаблоны на Node и Go — следующий шаг.
