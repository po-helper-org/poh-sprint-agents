# Сайдкары команд, merge и Python 3.9+

## Ситуация

Страницу отчёта нельзя было собрать без живого похода в трекер по всем командам сразу. Виджету нужен был режим «обновить только выбранные команды», а утреннему сбору — все; при падении одной команды не было способа показать свежие данные остальных.

## Причина

`run` собирал все команды за один проход и один HTML: частичное обновление и повторное использование чужих свежих данных не были предусмотрены. Конфиг читался `tomllib`, который есть только в Python 3.11+, а на серверах стоял 3.10.

## Решение

- **Сайдкары.** `run` после каждой успешной команды атомарно пишет `reports/teams/<slug>.json`. Упала одна — её прошлый сайдкар цел, у остальных свежие данные; HTML в этом случае не пишется, как и раньше.
- **`merge <slugs…>`.** Склеивает страницу из сайдкаров, в трекер не ходит, токен не нужен. Каждый сайдкар проверяется заново (схема и инварианты); старше `--stale-hours` (6 ч) отвергается, с `--stale-ok` — принимается с пометкой возраста; битый или отсутствующий — HTML не пишется. `--workspace` можно повторять — сводная страница нескольких проектов.
- **Python 3.9+.** На 3.11+ конфиг по-прежнему читает `tomllib`; на 3.9–3.10 — мини-парсер `runner/mini_toml.py`; сборщик и валидатор понимают даты трекера с `+0300` и `Z`.

## Как проверить

- `python3 -m unittest discover -s tests` — 114 тестов зелёные на Python 3.10.12 и 3.12.14.
- `run --only a` затем `merge a b` → HTML без единого запроса в трекер.
- `merge` со сайдкаром старше 6 часов → отказ; с `--stale-ok` → страница с пометкой возраста.

## Уроки

- Атомарный побочный артефакт на команду (сайдкар) дешевле кэша целиком: падение соседа не затрагивает чужие данные.
- Повторная валидация при merge обязательна: доверять файлу, который писался другим прогоном, нельзя.
- Мини-парсер TOML на stdlib закрыл разрыв версий Python без зависимости; проверяется тестом на равенство с `tomllib` там, где он есть.
