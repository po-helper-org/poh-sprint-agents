# Версии бизнес-блока: правки наслаиваются, пересбор данных их не стирает

## Ситуация

04.11 агент перестроил колоду GDS с OKR и KR: читалось хорошо. Через 3 минуты направления исчезли, остались автотексты из Jira («Закрыто: …; … и ещё 6»). Второй агент, записав блок, затёр правки, сделанные до него.

## Причина

- `attach()` выбрасывал весь блок, если `dataHash` не совпадал со снимком. Observe пересобирает снимок несколько раз в день (утро, «Актуализировать»), виджет сразу пересобирает колоду: 21:23 запись агента, 21:26 сбор GDS, и тексты пропали.
- Блок — один файл, который агент пишет целиком: последний писатель затирает всё, включая поля, которых он не касался.

## Решение

- Блок прикладывается и к более новому снимку; строки эпиков и историй, ушедших из спринта, отсеивает `prune()`. В `check` несовпадение хеша — предупреждение.
- `layers.py`: `apply` пишет версию `sprint-business.versions/vNNNN.json` только с полями, которые автор поменял к своей базе (`revision` в файле). Итог — наложение версий по хронологии, по полям (`objectives.<OBJ>`, `streams.<эпик>.<поле>`, `rows.<история>.<поле>`, остальное целиком). Одно поле поменяли двое — побеждает поздний, с предупреждением «перекрыта правка vN». Запись без `revision` ничего не удаляет. Записи под замком. Отклонённая запись не попадает ни в историю, ни в колоду.
- `business.py history` — кто, когда, что поменял.
