# /sprint-blockers — где и почему команда теряла время за квартал

## Ситуация

Отчёта «кого ждала команда и где стояли задачи за квартал» не существовало: был эталонный ручной отчёт «Простои из-за внешних зависимостей», но только по одной команде и руками.

## Причина

Данных ожиданий в трекере нет в готовом виде: есть история статусов, комментариев и связей — «ожидание» из них надо вывести. Учёта часов нет, мера — рабочие дни.

## Решение

Новый навык `/sprint-blockers`, конвейер из трёх шагов:

- `blockers.py fetch` — снимок задач периода через MCP-сервер Atlassian по stdio (или REST с токеном): в окружении, где трекер доступен только через официальный MCP, данные везёт скрипт, а не агент.
- `blockers.py facts` — ожидания по рабочим дням: приостановка + очереди ревью/теста ≥5 дней, у каждого доказательства (комментарии, связи); слабые сигналы отдельно. Ядро `waits.py` — модель случая из OSS `jira-agile-metrics` (MIT), код не подключён — плагин без зависимостей. Сравнение кандидатов (DevLake, jira-metrics-extract, коммерческие) — в `docs/sprint-blockers.md`.
- Агент разбирает каждое ожидание в случай (сторона, чего ждали, основание) или «не блокер»; `blockers.py apply` проверяет разбор (ключи из фактов, числа пересчитаны по датам) и собирает страницу.

Решения: установка и UAT по умолчанию не считаются (закрывают пачками), очереди короче 5 рабочих дней — не случай.

## Как проверить

- Числа сверены с эталоном: 66 рабочих дней в июле–сентябре, ожидание 17.08–17.09 — 23 дня (тесты `PeriodTest`, `WaitDaysTest`).
- `python3 -m unittest discover tests` — 304 OK, из них 48 новых; `blockers_mobile.mjs` — десктоп и телефон.
- Живой прогон на трёх командах: ~1400/680/1400 задач квартала за ~2 мин каждая.

## Уроки

- «Кого ждали» не даёт ни один готовый инструмент — модель случая (сторона + основание + интервал) поверх истории задач оказалась достаточной.
- Когда трекер только через MCP, транспорт встраивают в скрипт, а не в агента: агент не возит данные.
- Живые прогоны и ревью до слияния нашли с полдюжины счётных ошибок: дни случая с начала ожидания вместо периода (87 вместо 10), ответ MCP в одной записи с нотификацией терялся до таймаута, «Готово к проверке» в истории на английском не попадало в ревью, задачи без правок весь квартал не попадали в выборку. Первый разбор агента склеивал несвязанные ожидания — добавлена проверка пересечения по времени.
