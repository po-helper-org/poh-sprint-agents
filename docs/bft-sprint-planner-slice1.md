# БФТ — Навык планирования спринта (poh-sprint-agents, slice 1)

> Бизнес-функциональные требования на первый срез. Формат — адаптация
> корпоративного БФТ (БТ / ПТ / ФТ / НФТ / границы / трассировка / якоря) под
> внутренний навык, без JIRA-эпика и корпоративной вики. Планка качества сохранена:
> каждое требование ← источник, измеримость НФТ, границы системы, трассировка.

**Статус:** черновик на согласование. **Предмет:** навык `sprint-planner`
скрам-мастер-агента. **Каденс:** 6 стадий, STOP после каждой.

---

## 0. Контекст (As-Is → Gap → To-Be)

**As-Is.** Планирование спринта живёт в `poh-helper/sprint-planner` (PO-персона,
JIRA-BUILD). Отдельного скрам-мастер-контура нет. Накоплены замечания в issues
poh-helper (#68/#83/#84/#96/#70/#103/#138/#132/#47): нет операционного слоя
«кто/коммиты/даты», нет визуального консенсуса команды, capacity игнорирует
отсутствия, нет гейта готовности, декомпозиция «каждый навык по-своему».

**Gap.** Нет автономного навыка, который доводит спринт до **согласованного
плана с персональной декомпозицией и честной ёмкостью**, с нулём невыясненных
фактов и явным гейтом консенсуса.

**To-Be.** Навык `sprint-planner` (slice 1): из OKR/roadmap/факта прошлого
спринта строит согласованный ПЛАН + операционный контракт, всё в vault
(обратимо), материализация — за границей среза.

### 3.1 Структура ПЛАН-документа «что делаем в спринте» (ФТ-SP-7)

Заимствуется из po-helper (`ideal_sprint_plan.md` + `sprint_standards.md`),
**структура сохраняется** — она хорошо сгруппирована и годна для приёмки
PO-разработчиком. **8 верхнеуровневых блоков** фиксированного порядка
(блоков-целей может быть несколько — по числу активных OBJ):

1. **Шапка** — период, ответственный, статус (`📋 Планирование`).
2. **Блок на каждую ЦЕЛЬ (OBJ)** — список KR (со ссылками) · `🎯 Образ
   результата команды (Sprint Goal)` · **таблица историй** · доп. контекст и риски.
   Таблица — колонки фиксированного порядка:
   `ЭПИК | История | Образ результата | Образ действия | Исполнитель | Приоритет | SP`.
   Образ результата технических — `БЫЛО→СТАЛО`. Образ действия — атомарные шаги
   с тегами ролей `[SA]/[BE]/[FE]/[QA]/[RELEASE]/[PO]`, `[BLOCKER]`/`[RISK]`.
3. **Необходимые внеплановые работы** — та же таблица + колонка `Тег`.
4. **📊 Capacity по командам** — `Исполнитель | Ёмкость (SP) | Загрузка (SP) | Статус | Основная нагрузка`.
5. **👤 Персональный фокус** — `Исполнитель | Что показываю к концу спринта`
   (вторая оптика: что лично каждый показывает).
6. **⚠️ Общие риски** — `Риск | Mitigation`.
7. **🔭 Спринт N+1 (предварительно)** — образ результата + крупные истории без точного SP.
8. **Следующие шаги** — курсивом.

**Дельта slice 1 поверх эталона:** роли истории (#138) добавляются в таблицу/US;
секция Capacity учитывает реестр отсутствий (#84); операционный контракт
(ФТ-SP-4) — отдельный артефакт рядом с ПЛАН, раскрывающий «Персональный фокус» до
уровня «участник → задачи → ожидаемые даты» (коммиты — плановые ожидания текстом,
не git-сигнал в slice 1) (#68).

## 4. Нефункциональные требования (НФТ) — измеримые

| ID | Требование | Метрика |
|---|---|---|
| **НФТ-SP-1** | Точность | 0 фактов без источника в финальном ПЛАН (гейт deliver бинарный) |
| **НФТ-SP-2** | Обратимость | До consensus — 0 записей в трекер; всё в vault/git |
| **НФТ-SP-3** | Ёмкость | 100% отсутствий из реестра учтены; реестр актуализирован ≤ старта спринта (дата проставлена); отклонение план↔реестр = 0. На S1 velocity = fallback + `[УТОЧНИТЬ]` — не нарушение |
| **НФТ-SP-4** | Трассировка | 100% историй имеют поле KR или тег внепланового; 0 орфанов |
| **НФТ-SP-5** | Каденс | Диалог по одному вопросу за раз; STOP после каждой из 6 стадий |
| **НФТ-SP-6** | Проза | Деловая телеграфная, без AI-стоп-слов и декоративных эмодзи |
| **НФТ-SP-7** | Персональная ясность | 100% исполнителей имеют строку operational-contract с ≥1 ожидаемой датой |
| **НФТ-SP-8** | Приёмочная структура | `ПЛАН-{sprint}.md` содержит все 8 блоков эталона (§3.1); порядок и колонки не нарушены |

## 6. Открытые вопросы

- **Источник отсутствий** (#84): ручной реестр в domain-profile — дефолт slice 1;
  календарь/HR-коннектор — потом. Приватность: показывать факт «недоступен», не причину?
- **Board-поверхность** (#83): структурированный shareable markdown — slice 1;
  Excalidraw self-host — потом.
- **Роли истории** (#138): дефолт — **опционально, по фазам** (`[SA]/[BE]/[FE]/[QA]/[REL]`),
  не 4 обязательных на историю; автоподстановка из `team`-нексуса.
- **Канал правок команды** (#83): дефолт slice 1 — **PO ретранслирует правки устно
  на ревью**, агент версионирует board; прямой импорт доски — потом.
- **DoR ↔ 8 гейтов**: DoR — **вход** `/sm-decompose` (готовность истории к
  декомпозиции), 8 гейтов — **выход** `/sm-deliver` (валидация плана). Общий пункт
  «образ результата» не дублируется — DoR проверяет наличие, гейт 5 — качество.
- **Consensus-аудит**: фиксировать «кто согласовал» поимённо? (перекличка #66).
- **Стандарт декомпозиции** (#70): встроенный дефолт vs process-нексус. Дефолт
  встроенный, переопределение доменным профилем.
