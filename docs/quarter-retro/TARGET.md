# Разбор квартала — куда должны прийти

Эталон результата разбора квартала: **`ideal_quarter_fact.html`** — ФАКТ 2026Q3 команд GDS и Live, 50 KR в четырёх целях. Страница открывается в браузере как есть: клик по строке KR показывает детали, вкладка «Исход» слева фильтрует таблицу.

Эталон обезличен: люди заменены на «Участник Б…Э», внутренний идентификатор страницы Confluence убран. Структура, KR, проценты, шаги планов, риски и выводы — как в оригинале.

Этот документ фиксирует, **что именно** делает страницу хорошим итогом квартала. Будущий навык ретро (VISION: функция 4 «Корректировка квартала», срез 6 «Ретроспектива») должен выдавать результат этой формы и этого качества.

## Зачем этот результат

Разбор квартала отвечает на три вопроса, и страница отвечает на каждый явно:

1. **Что по факту сделано по каждому KR** — исход, процент, где именно встало.
2. **Что из этого следует для следующего квартала** — у каждого KR есть следующее действие и связь с KR нового квартала.
3. **Какие правила планирования поменять** — выводы сформулированы как правила, а не как пересказ, и есть базовая линия, чтобы через квартал проверить, стало ли лучше.

Страница не пересказывает квартал. Она закрывает его: каждый KR получает исход и следующий шаг, каждое сомнение — пометку `[УТОЧНИТЬ]`.

## Состав страницы (порядок фиксирован)

### 1. Шапка и паспорт факта

- Заголовок: `ФАКТ {квартал} — {команды}`.
- **Источник факта**: какая таблица или трекер, вкладка, команда, файл выгрузки, дата выгрузки, ступень основания.
- **Итог квартала**: среднее, взвешенное по PBV, с числом оценённых KR, и рядом простое среднее. Отдельно — что уточнил PO поверх выгрузки и по скольким KR.
- **Легенда статусов шагов**: `[x] сделано · [~] в работе · [ ] не начато · [-] снято · [?] статус не задан`. Здесь же правило для KR на 100 % и 0 % и список KR, размеченных со слов PO, с датой.

### 2. Таблицы KR по целям

Одна таблица на цель. Первая строка — **полоса цели**: `OBJ N — название · образ результата цели`. Если цель поменялась по ходу квартала, это пишется в полосе («Планы поменялись: витрина не закрывается…»).

Строка KR:

| Колонка | Содержимое |
|---|---|
| KR | идентификатор; `.E1` — эпик-предпосылка, `e` — внеплановая задача внутри KR |
| метка | `влёт` — KR пришёл после старта квартала (EKR) |
| PBV | вес бизнес-ценности; нет веса → `—`, вес 0 — отдельный сигнал |
| Название | с префиксом типа: `[RESEARCH]`, `[POC]`, `[FEAT]`, `[BUG]`, `[RELEASE]`, `[ACTIVITY]`, `[ТЕХДОЛГ]` |
| Прогресс | шкала этапов плана — одно деление на шаг, цвет по статусу шага, и `сделано / всего` |
| % | фактическая готовность; `ОТМ` для отменённых |

**Фильтр по исходу** со счётчиками: `✔ закрыт · ◐ частично · ✖ не сделано · ⊘ отменён`. Счётчики — это ровно число строк с этим исходом.

### 3. Карточка KR (по клику)

Порядок блоков:

1. `KR · OBJ`, название, `исход · % · PBV`, шкала этапов.
2. **Образ результата** — зачем KR, как было и как стало (`БЫЛО: … → СТАЛО: …`), критичность и перед кем коммитмент.
3. **Процессный roadmap** — шаги «роль + действие + статус» (`BA`, `SA`, `ADR`, `DBA`, `BE`, `FE`, `QA`, `DOPS`, `RELEASE`, `PO`, `DESIGN`, `VER`). `[EXT]` — работа другой команды.
4. **Зависимости** — в той же форме.
5. **Риски** — как их видели на старте квартала.
6. **Фактическая готовность** — процент и причина словами: «90 % — демо перенесли, DBA/DevOps, подключение к Production; коммитмент 30.09 сорван».
7. **Следующие действия** — одно из четырёх:
   - `Закрыт — снять с контроля`;
   - `Продолжается в {Q+1} — KR X` (связь с KR нового квартала);
   - `Отменён — записать причину и дату решения`;
   - `Решить: продолжаем, переносим или закрываем`.
8. **Исполнители** — роль и участник.

Статус шага берётся из источника, а не выводится моделью: «нет статуса» честнее придуманного TODO.

### 4. Сводка

Таблица исходов с долей и отдельной строкой — число внеплановых KR. Под ней один абзац о внеплановом: сколько пришло после старта, что именно, какая это доля объёма.

### 5. Что это говорит о правилах (калибровка)

Нумерованный список. Каждый пункт — **правило для следующего квартала, выведенное из конкретного факта**, с номерами KR:

1. **Демо ≠ готово.** KR 1.1 при 80 % сорвался на DBA/DevOps и подключении к Production → дата наружу только после прогона в целевом контуре.
2. **Слепая зона — чужие команды.** Внешние зависимости есть в трекере как риски, но без владельца и даты.
3. **Объём без оценки.** Строки с «—» и весом 0: непонятно, отменены они или до них не дошли руки.
4. **Внеплановое не учтено в ёмкости.** EKR съели ёмкость, которую никто не резервировал.
5. **Статус шагов не ведётся.** По частично выполненным KR не видно, где именно встало.

Пересказ «что было» сюда не попадает: только то, что меняет планирование.

### 6. Расхождения с ответами PO — проверить

`KR | что сказал PO | что в трекере | [УТОЧНИТЬ]`. Расхождение не разрешается молча в пользу одного источника: оно выносится отдельной строкой.

### 7. Базовая линия (день 1 следующего квартала)

Метрики, по которым через квартал проверяется, стало ли лучше:

| Метрика | Что фиксируем |
|---|---|
| Обещанных дат сдвинулось | из скольких коммитментов перед руководством |
| За сколько дней до срока узнали | лид-тайм сигнала о срыве |
| Часы в неделю на отчётность | `[УТОЧНИТЬ]`, пока не измерено |
| Сюрпризов в конце квартала | число внеплановых KR |
| Потоков на письменном основании | из скольких потоков |

## Критерии качества

Результат разбора квартала готов, когда:

- **У каждого KR есть исход, процент или `ОТМ`, и следующее действие.** Нет KR «повисших» без решения.
- **Каждый факт с источником.** Нет источника → `[УТОЧНИТЬ]`, а не догадка.
- **Процент объяснён словами**, если он не 0 и не 100: что сделано, где встало, почему.
- **Продолжение связано с KR нового квартала** (`Продолжается в 2026Q4 — KR 1.5`).
- **Отмена записана как решение**: причина и дата, а не молчаливое исчезновение строки.
- **Внеплановое видно**: метка `влёт` в строке и доля в сводке.
- **Выводы — правила**: каждый вывод меняет что-то в планировании следующего квартала и опирается на конкретные KR.
- **Расхождения источников вынесены**, а не сглажены.
- **Есть базовая линия** для сравнения через квартал.
- **Страница только читает**: правда живёт в `.md`, страница из него собирается. Один самодостаточный HTML без внешних зависимостей, айдентика страниц PO: ч/б, Georgia, моноширинные подписи, цвет только в статусах.

## Шероховатости экземпляра — в эталоне не повторять

Числа эталона сверены с данными самой страницы. Итог 92 % (взвешенное по PBV по 42 KR) и 86 % (простое среднее по 43) сходятся, счётчики фильтра совпадают со строками таблицы. Нашлось четыре мелочи, которые навык должен делать лучше:

| Где | Что не так | Как должно быть |
|---|---|---|
| Паспорт факта | `**92 %**` — markdown не отрендерен, звёздочки видны на странице | разметка из `.md` рендерится |
| Сводка | исходы `24 / 17 / 4 / 8` (сумма 53) расходятся с фильтром `25 / 15 / 3 / 7` (сумма 50) | одни правила группировки на всей странице; сумма = числу KR |
| Сводка | «внеплановых (EKR): 9», в абзаце «Десять KR», меток `влёт` 10 | одно число из одного источника — меток в таблице |
| KR 1.7 | в названии `(None)`, PBV `—` — сырой `null` из выгрузки | пустое поле не печатается; нет веса → `—` и пометка `[УТОЧНИТЬ: PBV]` |

KR 2.2 (95 % при шкале `0 / 8`) — не дефект вёрстки, а иллюстрация вывода №5: шаги не размечены («нет статуса»), поэтому шкала и процент расходятся. Навык ретро должен показывать такой KR так же честно, а не подгонять шкалу под процент.
