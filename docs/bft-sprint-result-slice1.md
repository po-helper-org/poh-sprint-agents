# БФТ — Навык отчёта по спринту (poh-sprint-agents, slice 2)

> Бизнес-функциональные требования на срез «спринт-ревью». Формат — тот же,
> что у `bft-sprint-planner-slice1.md`: БТ / ПТ / ФТ / НФТ / границы /
> трассировка / якоря. Каждое требование ← источник, НФТ измеримы.

**Статус:** согласован 08.09.2026, форма пересмотрена 09.09.2026 (§6, О8/О10). **Предмет:** навык `sprint-result`
скрам-мастер-агента. **Функции VISION:** 3 (спринт-ревью) и 5 (презентация).

---

## 0. Контекст (As-Is → Gap → To-Be)

**As-Is.** Навык `sprint-planner` доводит спринт до согласованного ПЛАН и
операционного контракта. На этом контур обрывается. Спринт закрывается вручную:
скрам-мастер вечером перед ревью собирает слайды, переписывая в них строки из
плана и вспоминая по памяти, что из обещанного вышло. Референсная колода
(§ `docs/reference/sprint-report-reference.md`) показывает результат такого
ручного цикла: 8 отчётов за три квартала, устойчивая структура — и в ней же
следы ручной сборки. Проценты готовности расставлены на глаз (`99%` у задачи,
которую откатили; `?` в ячейке результата); у части незакрытых строк нет
причины; строки живут из спринта в спринт, накапливая хвост комментария,
поэтому расхождение с планом накапливается вместе с ними.

**Gap.** Нет навыка, который превращает **обещания ПЛАН + фактический ход
спринта** в отчётный артефакт для бизнеса: с трассировкой каждой строки к
обещанию, с обязательным объяснением незакрытого и с доказуемым вердиктом по
Sprint Goal. Проблема-постановка PO: «текущие скиллы умеют планировать, но не
умеют генерировать отчётную презентацию».

**To-Be.** Навык `sprint-result` (slice 2): приводит любой входящий контекст к
единому формату отчёта. На выходе два артефакта — `ФАКТ-{sprint}.md`
(vault, под git, обратимо) и `ФАКТ-{sprint}.html` (отчётная страница, которую
показывают бизнесу и на которой же собирают правки). Правки со страницы
возвращаются в агент промтом и дают следующую версию. Материализация во
внешнюю презентацию — за границей среза.

## 1. Бизнес-требования (БТ)

| ID | Требование | Источник |
|---|---|---|
| **БТ-SR-1** | Агент выдаёт **доказуемый факт спринта**: что команда обещала, что вышло, чем это подтверждается | VISION Func 3; постановка PO |
| **БТ-SR-2** | Отчёт **читается бизнесом без контекста команды** — по нему принимают решение, а не расшифровывают | постановка PO «показать бизнесу что было сделано» |
| **БТ-SR-3** | Каждая строка отчёта **трассируется к обещанию ПЛАН** или явно помечена внеплановой | sprint-planner БТ-SP-2 (симметрия план↔факт) |
| **БТ-SR-4** | **Незакрытое объясняется всегда**: причина и следующий шаг — часть отчёта, а не вопрос с ревью | референс §3 |
| **БТ-SR-5** | **Ноль невыясненных фактов**: каждый процент, число и имя обоснованы источником | VISION принцип 1; sprint-planner БТ-SP-5 |
| **БТ-SR-6** | Отчёт **безопасен к публикации**: уходит наверх и живёт в переписке, поэтому не несёт учётных данных и внутренних ссылок | референс §6 |

### 3.1. Структура отчёта (ФТ-SR-7)

Каждый блок документа даёт слайд. Порядок фиксирован, соответствие эталонной
колоде — в скобках.

1. **Шапка** — спринт, период, ответственный, статус, версия, имя ПЛАН-файла.
   Даёт титульный слайд (§3 разбора).
2. **`## КОМАНДА: {название} — {перечень стримов}`** — HERO-разделитель.
   Одна команда → уровень не нужен (§2 разбора).
3. **`### СТРИМ: {название}`** — слайд с таблицей. Вердикт по Sprint Goal
   строкой, затем таблица трёх колонок фиксированной ширины:
   `Задачи (26%) | Комментарий (58%) | Результат (16%)`.
   Внеплановые работы — тоже стрим, тег уходит в префикс задачи.
4. **`## Изменения в процессе спринта`** — карточки `Было → Стало → Результат`.
5. **`## Демо`** — что показываем руками, кто показывает.
6. **`## Метрики`** — карточки: заголовок, скриншот от PO, объяснение.
7. **`## Итоги спринта`** — три счётчика (считает экспортёр по строкам) +
   «Ключевые риски и блокеры» + «Переносим в {sprint+1}». **Последним слайдом:**
   колоду читают линейно и вслух.

Блок пуст → слайда нет. Обязательны шапка, минимум один стрим и итоги.

**Правила формирования**, вынесенные в экспортёр, а не в инструкцию агенту:
сортировка строк по убыванию результата с подписью о ней; заливка строки
целиком по шкале; стоп-маркеры `🛑` (держит внешняя зависимость) и `🚫` (сняли
сами); разрез стрима, не влезающего в слайд, на «(продолжение)».

### 3.2. Гейты отчёта (ФТ-SR-2)

Девять бинарных гейтов по образцу `resources/hard_gates.md`. Светофор тот же:
🔴 при нарушении 1–5 — запись блокируется; 🟡 при 6–9 — запись с явными
`[УТОЧНИТЬ]` под риск PO.

| # | Гейт | Правило |
|---|---|---|
| 1 | Трассировка | Каждая строка ← строка ПЛАН или стоит во «Внеплановых» с тегом. 0 строк-сирот, 0 потерянных строк ПЛАН |
| 2 | Объяснимость | Строка с `Результат` < 100% несёт `Причина:` и `Следующий шаг:` |
| 3 | Вывод процента | Процент **выведен по лестнице готовности** (референс §4.1) из образа результата ПЛАН: названа пройденная ступень, из неё следует число. PO подтверждает или правит на ресинке. Ступень не определяется → `[УТОЧНИТЬ]`, не оценка на глаз |
| 4 | Вердикт | У каждой цели есть вердикт по Sprint Goal с доказательством (что показываем) |
| 5 | Чистота публикации | 0 паролей/токенов/ключей; 0 внутренних URL вне вайтлиста домен-профиля; ФИО — только из ростера |
| 6 | Читаемость | Строк на стрим ≤ 6 — столько влезает в слайд. Экспортёр режет механически, содержательный разрез — решение PO |
| 7 | Метрика с объяснением | Каждый скриншот несёт объяснение текстом; голых цифр и пересказа графика агентом нет |
| 8 | Перенос назван | Незакрытые строки перечислены поимённо в блоке «Переносим в {sprint+1}», каждая с процентом и причиной |
| 9 | Регистр текста | caveman ultra + anti-slop; проверяется `sprint-report-style-lint.py`. **🟡 при сборке, 🔴 на финализации** |

Гейт 5 — блокирующий и в режиме `🟡`: отчёт с учётной записью внутри не
пишется на диск ни при каком решении PO.

**Машинная часть гейтов** — два валидатора, прогон обязателен до сборки колоды
и повторно до финализации (ФТ-SR-10): `check_report_structure.py` закрывает
гейты 2, 3, 4, 6 и структуру, `sprint-report-style-lint.py` — гейт 9. Гейты 1,
5, 7 остаются агентными: валидатор не знает ПЛАН, вайтлиста и слов PO.

## 4. Нефункциональные требования (НФТ) — измеримые

| ID | Требование | Метрика |
|---|---|---|
| **НФТ-SR-1** | Точность | 0 фактов без источника в финальном ФАКТ; у 100% строк процент сопровождён названной ступенью лестницы |
| **НФТ-SR-2** | Обратимость | Всё в vault под git; публикация во внешнюю систему — ручное действие PO, агент не публикует |
| **НФТ-SR-3** | Полнота план/факт | 100% строк ПЛАН имеют строку в ФАКТ: закрыта, перенесена или снята с обоснованием. 0 молча пропавших |
| **НФТ-SR-4** | Объяснимость | 100% строк < 100% несут причину и следующий шаг |
| **НФТ-SR-5** | Читаемость бизнесом | Колода читается без докладчика: вердикт у каждого стрима + итоговый слайд. Строк на стрим ≤ 6 — столько влезает в слайд 720px |
| **НФТ-SR-6** | Чистота публикации | 0 учётных данных, 0 внутренних URL вне вайтлиста, 0 ФИО вне ростера — в `.md` и в `.html` |
| **НФТ-SR-7** | Регистр | caveman ultra + anti-slop; 0 совпадений `sprint-report-style-lint.py` на финальной версии |
| **НФТ-SR-8** | Приёмочная структура | `ФАКТ-{sprint}.md` соответствует §3.1: порядок блоков и три колонки не нарушены (структурный валидатор) |
| **НФТ-SR-9** | Цикл правок | Правка со страницы → новая версия за один прогон `/sr-revise`; круг фиксируется, закрытые правки в следующий промт не попадают |
| **НФТ-SR-10** | Автономность колоды | `.html` открывается с диска и работает без сети; при показе и печати механики правок не видно |

## 5. Границы системы

**ВНУТРИ slice 2:** ресинк факта, сборка `ФАКТ-{sprint}.md` по эталону,
рендер отчётной страницы, цикл правок «страница → промт → версия», гейты
отчёта, структурный валидатор, симметрия план/факт.

**СНАРУЖИ (следующие срезы):** выгрузка статусов из трекера (сейчас статусы
приходят из ресинка с PO); автоматический сбор процессных метрик (сейчас —
скриншот от PO, О4); слайд-режим страницы (О8); генерация
`.pptx`/Google Slides; daily-каденс как источник факта; ретроспектива и
персональная память; публикация страницы куда-либо, кроме файла на диске.

## 6. Решения PO и оставшиеся вопросы

Согласовано 08.09.2026.

| # | Вопрос | Решение |
|---|---|---|
| **О1** | Единица блока: направление работ (референс) или цель OBJ (ПЛАН)? | **Одна сущность — стратегическая инициатива.** Направление, OBJ-срез квартала и заголовок слайда — один уровень декомпозиции (`decomposition_standard.md`, ИНИЦИАТИВА). Блок = инициатива; симметрия план/факт сохраняется |
| **О2** | Источник процента готовности | **Вывод из образа результата ПЛАН** по лестнице готовности (референс §4.1): агент называет пройденную ступень и следующий из неё процент, PO подтверждает или правит. Гейт 3 проверяет наличие названной ступени, а не самого числа |
| **О3** | Блок «Итог для бизнеса» — в референсе его нет | Добавляем: без него страница не живёт без докладчика (ПТ-SR-1) |
| **О4** | Процессные метрики в slice 2 | **PO прикрепляет скриншоты дашборда отдельно**, агент добавляет объяснение с его слов. Агент не читает графики и не пересказывает цифры. Скриншотов нет → блок не пишется |
| **О5** | Вайтлист внешних ссылок (гейт 5) | Пусто по умолчанию — любая ссылка требует явного разрешения в домен-профиле |
| **О6** | Carryover-мост в следующий спринт | Автоматически: `/sm-sync` уже читает `sprint_fact_doc`, формат совпадёт |
| **О7** | Демо-артефакты: вкладывать или ссылаться | Ссылка + подпись, как и метрики (О4). Вложение файлов — следующий срез |
| **О8** | Форма `.html` | ~~Документ-страница~~ → **пересмотрено 09.09.2026 по эталону PO: колода слайдов 1280×720.** Механика правок из `poh-bft-writer` сохранена, но убрана в поля и не печатается |
| **О10** | Где показывать ступень лестницы (решение О2), если в эталоне ячейка результата несёт только число | **В подсказке ячейки.** В `.md` ступень есть и проверяется гейтом 3, на слайде её нет — так в эталоне |

| **О9** | **Откуда планировщик берёт velocity?** Найдено при стыковке навыков: `sprint-planner` резолвит velocity из ФАКТ прошлых спринтов, но ФАКТ не несёт SP — «закрыто SP» по человеку это персональная оценка, которой в отчёте для бизнеса быть не должно (решение Д3). Планировщик остаётся на fallback `sp_per_person_sprint` и метку `[УТОЧНИТЬ velocity]` не снимает никогда | **Открыт.** Варианты: (а) служебный файл `velocity-{sprint}.md` рядом с ФАКТ — цифры есть, в отчёт не попадают; (б) блок план/факт по ёмкости внутри ФАКТ — противоречит Д3; (в) остаться на fallback и признать, что velocity не резолвится. До решения PO навык ничего не додумывает |

**Остаётся открытым к этапу реализации:** порог «сколько строк на инициативу
до разреза» (НФТ-SR-5 фиксирует ≤ 6 по референсу — проверяется на первом
живом прогоне).
