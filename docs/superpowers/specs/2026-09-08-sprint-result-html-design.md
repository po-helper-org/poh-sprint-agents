# Design — отчётная страница спринта (`ФАКТ-{sprint}.html`)

**Дата:** 2026-09-08 · **Статус:** согласован 08.09.2026 (§10) ·
**БФТ:** `docs/bft-sprint-result-slice1.md` (ФТ-SR-3, ФТ-SR-8, НФТ-SR-5/9/10) ·
**Макет:** `docs/reference/sprint-report-page-mockup.html` (рабочий, открывается с диска)

## 1. Цель

Страница — **формат-мишень**: к этой раскладке навык `sprint-result` приводит
любой входящий контекст. Она же рабочая поверхность двух разных встреч:
на ревью по ней докладывают бизнесу, после ревью на ней же собирают правки.
Из этого следуют два требования, которые тянут раскладку в разные стороны:
читаться сверху вниз без докладчика — и принимать комментарий в любую строку.

Решение: **документ, а не слайды** (решение PO О8). Комментарий живёт в потоке
текста, а вся служебная механика правок убрана в поля — рейку слева и угол
справа, — чтобы при показе и при печати её не было видно.

## 2. Происхождение визуала

Типографика и механика — порт из `po-helper-org/poh-bft-writer`
(`skills/bft-writer/scripts/bft-html-export.{css,js}`): чёрно-белый документ,
Georgia, колонка 860px, выезжающая рейка слева, комментарии → промт справа,
круги правок по хэшу содержимого. Порт даёт узнаваемость между артефактами
контура и снимает изобретение движка заново.

**Дельта поверх порта — цвет.** У БФТ палитры нет вовсе. Отчёту цвет нужен:
шкала готовности — то, по чему бизнес читает страницу за три секунды. Взята
палитра источника (референсная колода): зелёный `#d9ead3`, жёлтый `#fff2cc`,
красный `#f4cccc`, серый `#eeeeee`. Цвет на странице ровно один и несёт
статус — поэтому заливки «для красоты» нет нигде: рядом с осмысленной она
читалась бы как ещё один статус.

## 3. Раскладка

Порядок блоков — из БФТ §3.1, один в один. Слева номер блока БФТ.

| # | Блок | Как выглядит |
|---|---|---|
| 1 | Шапка | `ФАКТ | {спринт}` крупно + строка метаданных моноширинным: период, ответственный, статус, версия, имя ПЛАН-файла |
| — | **Светофор спринта** | Полоса на всю ширину: доли закрытых / в работе / не начатых / фоновых строк, под ней легенда шкалы. Не блок БФТ, а его визуальная свёртка: первый экран отвечает «как прошёл спринт» без чтения |
| 2 | Итог для бизнеса | 3 абзаца прозой, первый крупнее. Единственное место со свободным текстом |
| 3 | Инициатива (× N) | Заголовок = название инициативы · надзаголовок «инициатива K из N» · строка KR моноширинным · **плашка вердикта** · таблица строк |
| 4 | Внеплановые работы | Та же таблица, четвёртая колонка — тег-чип вместо OKR |
| 5 | Изменения в процессе спринта | Карточка: «затронуто», две колонки `Было` / `Стало`, под ними результат с отбивкой |
| 6 | Процессные метрики | `<figure>`: место под скриншот PO + подпись «Объяснение». Скриншота нет → блока нет |
| 7 | Демо | Список: что показываем, кто, сколько минут, ссылка на запись |
| 8 | Перенос и следующие шаги | Список кандидатов в carryover с процентом и причиной + шаги курсивом |

**Плашка вердикта** — рамка с толстой левой чертой в цвет статуса
(`достигнут` / `частично` / `не достигнут`) и текстом в три хода:
что обещали · что показываем · чего не показываем. Это гейт 4 БФТ, вынесенный
в вёрстку: пустую плашку видно сразу.

## 4. Ячейка «Результат» — число и его происхождение

Ячейка заливается по шкале и несёт **две строки**: процент крупно и **ступень
лестницы готовности** мелким моноширинным под ним («в Production»,
«ревью пройдено», «разработка не начата, аналитика есть»).

Вторая строка — не украшение, а гейт 3 БФТ в вёрстке. Решение PO О2: процент
не называется, а выводится из образа результата ПЛАН по лестнице
(`docs/reference/sprint-report-reference.md` §4.1). Пустая вторая строка на
странице означает невыведенный процент — то самое, что гейт запрещает.
`ACTIVITY` и `заблокировано` занимают место процента и заливаются серым:
это не «плохо», это «шкала неприменима».

## 5. Ячейка «Комментарий» — помеченные строки, не абзац

Микро-грамматика референса (§3 разбора) отражена типографикой, у каждой метки
свой вес:

| Метка | Оформление | Почему так |
|---|---|---|
| `Образ результата` | приглушённый серый | обещание из ПЛАН, фон для факта |
| `Факт` | основной чёрный | то, ради чего строку читают |
| `Причина` | левая красная черта | вопрос бизнеса №1 к незакрытой строке |
| `Блокатор` | левая красная черта, метка красная | не вина команды, но и не прогресс |
| `Следующий шаг` | левая серая черта | ответ на «что дальше» |
| `Созависимые` | обычный | кто нужен извне |

Читатель сканирует колонку по вертикали и видит, где красное. Абзац сплошного
текста (как в источнике) такого не даёт.

## 6. Цикл правок (ФТ-SR-3, НФТ-SR-9)

- **Клик по строке таблицы** → попап комментария, привязанный к этой строке.
  Строка получает зелёную отбивку слева.
- **Выделение любого текста** → тот же попап, привязка к фрагменту и разделу.
  Раздел определяется ближайшим заголовком выше: агент правит раздел, а не
  «третий абзац сверху».
- **Точка у `[УТОЧНИТЬ]`** — пульсирует красным, по клику открывает тот же
  попап. Отвеченная перестаёт пульсировать.
- **Рейка слева**: «Содержание» (строится из фактических `<h2>`, не
  хардкодится) и «Правки» (обход всех открытых замечаний).
- **Угол справа**: счётчик правок, панель со списком, готовый промт и кнопка
  «Скопировать промт». Отдельно — «Отчёт финальный»: считает незакрытые правки
  и отдаёт команду `/sr-final {sprint}`.
- **Круг правок.** Страница несёт хэш содержимого. Пересобрали отчёт — хэш
  сменился, открытые правки получают дату закрытия и в следующий промт не
  попадают. Иначе агент получает уже выполненное второй раз.

Правки живут в `localStorage`, не в файле: они превращаются в промт и уходят в
чат, а не остаются частью артефакта. Файл открывается с диска и работает без
сети (НФТ-SR-10).

## 7. Печать и показ

`@media print` убирает рейку, угол и попапы, снимает ограничение колонки,
запрещает разрыв строки таблицы. Отчёт печатается и уходит в переписку тем же
файлом. Слайд-режим для показа на ревью — отдельный срез (О8).

## 8. Как страница собирается

```
ФАКТ-{sprint}.md ──► sprint-report-html.py ──► ФАКТ-{sprint}.html
                       │
                       ├── sprint-report.css   (эта раскладка)
                       └── sprint-report.js    (цикл правок)
```

Экспортёр — python3 без сторонних зависимостей, по образцу
`bft-html-export.py`: разбор ограниченного markdown (заголовки, абзацы,
списки, таблицы, инлайн), затем доменные преобразования:

1. Колонка `Результат` → класс заливки + разбор ступени (`100% · в Production`).
2. Ячейка `Комментарий` → помеченные строки по меткам микро-грамматики.
3. Вердикт из блока инициативы → плашка.
4. Подсчёт строк по статусам → светофор спринта.
5. `[УТОЧНИТЬ]` → `<mark>` + точка.
6. Ключи трекера → ссылки **только по вайтлисту домен-профиля** (решение О5:
   вайтлист пуст по умолчанию, без него ключ остаётся текстом).

Макет `sprint-report-page-mockup.html` — не картинка, а рабочая страница с
синтетическими данными: он и есть шаблон, в который экспортёр подставляет
содержимое. Расхождение макета и выхода экспортёра — дефект экспортёра.

## 9. Границы

Не делаем в этом срезе: слайд-режим, вложение файлов в страницу (скриншоты и
записи демо — ссылками, О4/О7), тёмную тему (документ печатный, палитра
источника светлая), рендер диаграмм, синхронизацию правок между устройствами.

## 10. Решения PO

Согласовано 08.09.2026.

| # | Вопрос | Решение |
|---|---|---|
| **Д1** | Светофор считает строки или взвешивает по SP? | **Строки.** SP в ФАКТ не переносятся, а взвешивание по SP даёт «закрыли 80% спринта» при двух незакрытых Must |
| **Д2** | Порог разреза инициативы (НФТ-SR-5: ≤ 6 строк) | **Предупреждать.** Гейт 6 отдаёт 🟡 и называет инициативу; разрез — решение PO, агент не режет сам |
| **Д3** | Показывать ли исполнителя в отчёте для бизнеса | **Ролью** (`[BE] BE-1`), как в макете: вклад виден (ПТ-SR-6), персональной оценки нет |
