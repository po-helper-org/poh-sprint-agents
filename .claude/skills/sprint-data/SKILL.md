# Навык: данные отчётов — JSON команды и его сборщик

## Роль
Ты — автор и проверяющий сборщика данных. Отчёт PO (`/actual-sprint`), презентация «ФАКТ | спринт» (`/sprint-business`), PDF-статус (`/sprint-status`) и факты для ИИ (`/sprint-insights`) читают один и тот же JSON команды. Этот навык отвечает за то, чтобы JSON был, был полным и был правдой.

## Коротко
| Вопрос | Ответ |
|---|---|
| Какая структура у JSON? | `actual-sprint/contract/team.schema.json` — машинная форма; образец со всеми полями — `actual-sprint/examples/example_team_full.json` |
| Как JSON становится отчётом и презентацией? | детерминированно, кодом страниц, без модели — `reference/render.md` |
| Что значит каждое поле, какого оно типа, зачем и откуда? | `reference/fields.md` — достаточно, чтобы любой агент написал сборщик под свою систему |
| Можно ли собрать JSON без скрипта? | нет: только скрипт, подключённый к источнику, — правило ниже |
| Как написать скрипт для JIRA? | `guides/jira.md` + рабочий пример `actual-sprint/templates/python/collector.py`; стадии `/collector-new`, `/collector-validate` |

## Правило: данные — только из скрипта, подключённого к источнику
1. **JSON команды делает скрипт-сборщик**, который сам ходит в систему-источник (JIRA или другую) и выдаёт JSON по контракту. Запускает его runner. Нет скрипта или нет подключения — нет отчёта: презентация обязана соответствовать действительности, а соответствие держится только на воспроизводимом сборе.
2. **Модель — не источник данных.** Не собирает JSON вызовами инструментов, не дописывает и не правит JSON или снимок `reports/sprint-report.data.json`, не подставляет числа по памяти. Пустой слайд лечится сборщиком (добавить секцию), а не данными руками.
3. **MCP и ручные запросы к трекеру — для разведки и сверки**: найти доску, поля, имена статусов; сверить выборку из `run.py validate` поле за полем. Не для отчётных цифр.
4. **Сборщик проверен до первого отчёта**: схема, 14 инвариантов, сверка выборки с трекером, подтверждение PO, хеш в `sprint-report.lock.json`. Изменился хоть на байт — проверка заново.

## Как JSON становится отчётом
```
источник (JIRA REST)
   └─► сборщик: скрипт по протоколу 1 (stdin — запрос, stdout — JSON команды)
         └─► runner run.py: схема + 14 инвариантов (+ покрытие экранов в validate/check)
               └─► снимок reports/sprint-report.data.json — массив TEAMS
                     ├─► отчёт PO        reports/sprint-report.html      run.py run / render
                     ├─► презентация     reports/sprint-business.html    business.py apply / render
                     ├─► PDF-статус      /sprint-status                  status.py
                     └─► факты для ИИ    insights.py facts, business.py facts
```
Страница = шаблон + тот же массив `TEAMS`, вставленный вместо `{{TEAMS_JSON}}`. Всё производное — средние, коридоры, прогнозы, группировки по участникам — считает в браузере код `actual-sprint/resources/shared/core.js` из полей JSON, без модели: одинаковый JSON — одинаковые слайды. Тексты ИИ (интерпретация, бизнес-формулировки) лежат в отдельных файлах и прикладываются к данным, только если их хеш совпал с хешем сбора. Что от какого поля зависит — `reference/render.md`.

## Стадии (STOP после каждой)
1. **Подключение** — `/sprint-setup`: адрес и токен через переменные окружения, CA-бандл, команды и доски в `sprint-report.config.toml`.
2. **Сборщик** — сначала базовый с `params` (типы историй, поле эпика, поле SP, бакеты статусов, окна). Свой код — только когда отличается алгоритм или система: `/collector-new` по `guides/jira.md` или `guides/other-sources.md`.
3. **Проверка** — `/collector-validate`: `run.py validate <slug>` (схема, инварианты, покрытие экранов, выборка), сверка выборки с трекером, «да» PO, `run.py lock <slug>`.
4. **Сбор** — `/actual-sprint`: `run.py run` пишет отчёт PO и снимок; презентация — `/sprint-business`.

## Почему слайд или график пустой
```bash
python3 .claude/skills/actual-sprint/runner/run.py check reports/sprint-report.data.json
```
Печатает схему, инварианты и покрытие: каждый экран отчёта PO, презентации и PDF — данные есть / частично / нет, и каких полей не хватает. Ответ человеку — «сборщик не отдаёт `<поле>`, нужен сборщик X.Y+ или правка `<функция>`», не «сейчас допишу». `check` принимает и один объект команды, и снимок-массив.

## Изменение контракта
Новый график, которому нужны новые данные, проходит по порядку: поле в `team.schema.json` → описание в `reference/fields.md` → строка в `reference/render.md` и в покрытии (`runner/validate.py`, `COVERAGE`) → сбор в базовом сборщике (с повышением `VERSION`) и в `guides/jira.md` → демо-данные (`scripts/demo_data.py`) и образец (`demo_data.py --example examples/example_team_full.json`) → тесты (`tests/test_contract.py` сверяет схему, справочник и образец между собой). Форма данных не меняется молча: несовместимое изменение повышает `protocol`.

## Границы
Сборщик только читает источник: ни одного запроса, меняющего трекер. Проверка TLS не отключается, токен живёт только в переменной окружения. Время — только `now` из запроса.
