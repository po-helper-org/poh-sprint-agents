# Как JSON становится отчётом и презентацией

Модель в этом пути не участвует. Страница — это шаблон, общий движок и массив `TEAMS` (снимок `reports/sprint-report.data.json`), вставленный вместо `{{TEAMS_JSON}}` (`actual-sprint/runner/build.py`: `assemble` → `render`). Дальше браузер рисует всё сам кодом `actual-sprint/resources/shared/core.js` и шаблона: одинаковый JSON — одинаковые экраны, без сети.

| Что | Шаблон | Кто собирает |
|---|---|---|
| отчёт PO | `actual-sprint/resources/report_template.html` | `run.py run` (после сбора), `run.py render` (из снимка) |
| презентация «ФАКТ \| спринт» | `sprint-business/resources/business_template.html` | `business.py render` / `apply` (из снимка) |
| PDF-статус | `sprint-status/page.py` | `status.py` (из снимка) |

**«Сегодня» страницы** — `_meta.collectedAt`: окна «3 спринта», сгорание эпика, прогноз, «застряли» на слайде считаются от момента сбора, поэтому презентация, открытая через неделю, показывает тот же снимок. Исключение — метка возраста статуса в отчёте PO (`ageHtml`): она нарочно считается от момента открытия, чтобы рабочая страница не «протухала».

**Бакет статуса** везде один: `statusMap[status]`, нет в карте — правила `classifyBucket(status, category)`. Группы: «Не начато» — `open`, `blocked`; «В работе» — `progress`, `review`, `testing`; «Выполнено» — `done`.

**Тексты ИИ не меняют цифр.** `insights` (наблюдения, интерпретация «!») и `business` (цели, KR, формулировки, планы, риски) лежат в своих файлах и прикладываются к команде, только если их `dataHash` совпал с хешем её данных (`build.team_digest`). Нет текста — страница пишет строку из данных.

## Отчёт PO

| Экран | Поля | Что считает страница | Без данных |
|---|---|---|---|
| таблица эпиков, панель эпика | `epics[]`, `epics[].stories[]`, `epics[].stories[].subtasks[]` | счётчики `open/blocked/progress/testing/review/done` по всей иерархии: история и каждая её подзадача — единица (`tallyEpic`) | таблица пуста |
| исполнитель и возраст статуса в панели | `stories[].assignee`, `stories[].statusChanged`, `subtasks[].assignee`, `subtasks[].statusChanged` | инициалы «ФИ» (`whoHtml`); дни без смены статуса, красным дольше 3 дней, у готовых — зелёным (`ageHtml`) | «—» |
| приоритет задач и эпиков | `stories[].priority`, `subtasks[].priority`, `epics[].epicPriority` | глиф `⇈ ↑ = ↓ ⇊` по имени приоритета (`prioHtml`) | «·» |
| Lead Time в шапке | `metrics.overall.lead` | `среднее / медиана / кол-во` как есть | «—» |
| метрики: burndown спринта | `burndown.days[]` | идеальная прямая от объёма первого дня с задачами до нуля к `end`; факт `remaining` до последнего не-`future` дня; выходные затенены (`burndownChart`) | «Нет данных по спринту» |
| метрики: производительность | `velocity.sprints[]`, `velocity.avgDone` | пара столбцов на спринт: `planned` стопкой по `split`, `done`; пунктир — `avgDone` (`velocityChart`) | график пуст |
| метрики: диаграммы управления | `control.stories`, `control.subtasks` | точки `doneAt × cycle`, выбросы (`outlier`), скользящее среднее по 5 задачам и коридор ±σ, порог `limit`, зона риска `risks` у правого края; списки выбросов и риска (`controlChart`) | «Нет закрытых …» |
| лента «Logs» | `logs.events[]`, `logs.kinds`, `logs.authors` | фильтры по виду и автору, группировка по дням | лента пуста |
| «Команда: N участников» | `output.sprints[].members[]`, `output.lead` | последние 3 спринта: выполнено «из» всех в SP (или задачах), три группы статусов, Lead time участника (`outputModel`, `memberTable`) | ссылки «Команда» нет |
| задачи участника по клику | `output.sprints[].members[].items[]` | задачи по спринтам, сначала «Выполнено — в зачёт»; по клику — `history` и `comments` (`openMember`) | «нужен сборщик 1.4.0+» |
| «Весь эпик» и сгорание эпика | `epics[].scope[]`, `scope[].created`, `scope[].doneAt`, `scope[].sprint`, `scope[].inSprint` | «Сделано X из Y», разделы «Что осталось» / «Что выполнено»; сгорание по неделям (`epicBurn`): последние 10 недель, выполнено / осталось / добавлено, темп — среднее выполненное за 3 последние недели, прогноз `today + 7 · ⌈осталось / темп⌉` | кнопки «Смотреть весь эпик» нет |
| сгорание эпика: основа SP | `scope[].sp` | вес задачи = SP, без оценки — в счётчике «без оценки» | все задачи «без оценки» |
| сгорание эпика: по подзадачам | `scope[].subtasks[].created`, `scope[].subtasks[].doneAt` | вес подзадачи = 1 | режим подзадач пуст |
| плановая дата эпика | `epics[].epicDue` | красная линия «план»; итог = прогноз − план в днях: ≤ 0 зелёный, ≤ 7 жёлтый, больше — красный | без плана и итога |

Сверху — «!» (интерпретация ИИ, `insights.interpretation`) и раздел «Инсайды ИИ» (`insights.observations`): наложение, не данные сборщика.

## Презентация «ФАКТ | спринт»

| Экран | Поля | Что считает страница | Без данных |
|---|---|---|---|
| титул и слайд команды | `epics[].stories[]`, `burndown.days[]`, `sprintName`, `team` | историй всего, готово, в работе, заблокировано (`teamStats`); день спринта N из M по рабочим дням (`teamPace`) | нет сводки |
| слайд команды: SP за спринт | `output.field`, `output.sprints[-1].members[].split` | SP выполнено из всех в текущем спринте | без SP |
| слайды целей: строки историй | `epics[].stories[]` (+ `subtasks`, `statusChanged`), `business.rows`, `business.streams`, `business.objectives` | слайд = цель OBJ, группа = KR (эпик), строка = история; результат: закрыта — 100%, иначе большее из стадии (в работе 30, тест 80, ревью 90) и доли закрытых подзадач, не выше 90% (`storyResult`); без бизнес-текста — «Сделано: …» по закрытым подзадачам, «в работе с dd.mm» по `statusChanged`, след. шаг — первая незакрытая подзадача (`autoText`) | нет строк / дат «с …» |
| клик по KR: сгорание эпика | `epics[].scope[]`, `epics[].epicDue` | тот же «Весь эпик», что в отчёте PO (`renderScope`) | только задачи спринта |
| клик по истории: календарь и хронология | `epics[].stories[].events[]` | календарь: статус истории полосой по дням, события подзадач, комментарии; лента по времени с фильтром «Все / История / Подзадачи» (`storyCalendar`, `storyFeedHtml`) | события только из ленты спринта (`logs`) |
| операционный: производительность | `output.sprints[].members[].split` | последние 3 спринта: план на конец спринта по трём группам и выполнено, пунктир — среднее выполненное закрытых спринтов (`teamOutputChart`) | `velocity` в задачах вместо SP |
| операционный: сгорание спринта | `burndown.days[]` | как в отчёте PO | график пуст |
| операционный: истории и подзадачи по участникам | `stories[].assignee`, `subtasks[].assignee`, `stories[].statusChanged`, `subtasks[].statusChanged` | строка на исполнителя: полосы его историй и его подзадач по статусам, «сделано/всего»; застряли — не `done` и не `open`, статус не менялся больше 3 дней на момент сбора: число · самое долгое; шкала «Числа / Доли», сортировка (`memberMatrix`) | всё у «Не назначен», застрявших нет |
| «Сроки»: cycle time по спринтам | `control.stories.points[]`, `control.subtasks.points[]`, `output.sprints[].start`, `output.sprints[].end` | окно — от начала первого из трёх спринтов (иначе 6 недель до сбора); полосы спринтов; точки двух потоков; скользящее среднее по 5 последним задачам потока и коридор ±σ того же окна; значение в конце линии (`cycleChart`) | нет точек / полос спринтов |
| «Сроки»: время в статусах | `output.sprints[].timeInStatus` | «Заблокировано» (`blocked`), «Ревью» (`review`), «Отладка» (`testing`): текущее крупно, столбики по спринтам (`statusTimePanel`) | «нужна версия 1.8.0» |
| «Сроки»: разбор, зона риска | `control.*.points[]`, `control.*.risks[]` | по клику: в окне 3 спринтов пересчитаны медиана, среднее, σ, порог `среднее + σ`, выбросы, зона риска выше медианы окна (`controlWindow`); классическая диаграмма управления и таблица по спринтам (`openControl`) | зона риска пуста |
| «Планы»: взять в работу | `epics[].scope[]` (вне спринта, бакет `open`), строки историй | «Доделать» — незакрытые истории спринта по убыванию результата, «Эскалировать» — заблокированные, «Взять в работу» — открытые задачи KR вне спринта; `business.plans` агента заменяет колонку (`planCards`) | колонка из бизнес-блока или пуста |

Остальные слайды — «Изменения» (изменение объёма по `burndown` + `business.changes`), «Демо», «Итоги» (счётчики по результатам строк, блокеры по давности `statusChanged`), «Риски» — из тех же строк и бизнес-блока.

## PDF-статус

| Экран | Поля | Что считает | Без данных |
|---|---|---|---|
| KPI, burndown, «Внимание» | `burndown.days[]`, `epics[].stories[]` (+ `statusChanged`), `control.stories.risks[]`, `_meta` | готово, темп против идеала, за сутки, блокеры, без движения больше 3 дней, зона риска, прогресс эпиков; подвал — свежесть `_meta.collectedAt` (`sprint-status/model.py`) | без темпа и «без движения» |

## Проверка покрытия
Таблицы выше — те же экраны, что в `COVERAGE` (`actual-sprint/runner/validate.py`). По готовому JSON:
```bash
python3 .claude/skills/actual-sprint/runner/run.py check reports/sprint-report.data.json --all
```
`✓` — данных хватает, `◐` — часть полей не отдана, `✗` — экран пуст; рядом — каких полей нет и что увидит читатель.
