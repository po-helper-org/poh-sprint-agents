# Коннектор JIRA — источник фактов о задачах

Раздел «Управление спринтами» (`plugins/dsh-plugin-sprint`) даёт среде три
инструмента чтения корпоративной JIRA. Они есть не всегда: в DeepSeek Harness с
установленным разделом — да, в голом окружении — нет. Правило простое:
**инструменты доступны → факты о задачах берём оттуда; недоступны → работаем по
волту, как раньше.**

| Инструмент | Что отдаёт | Когда звать |
|---|---|---|
| `jira_current_stories` | истории и задачи активного спринта проекта команды | ресинк контекста, carryover, «что уже в работе» |
| `jira_search` | выдача по своему JQL | прошлый спринт, баги, техдолг, метки, другой проект |
| `jira_issue` | одна задача с описанием | детали конкретной истории перед декомпозицией |

## Где это помогает в пайплайне

| Стадия | Что подтянуть |
|---|---|
| `/sm-sync` | carryover прошлого спринта, открытые баги и техдолг — фактом из трекера, а не вопросом к PO |
| `/sm-decompose` | существующие эпики и ключи задач вместо `TBD` в колонке ЭПИК |
| `/sm-load` | фактическая загрузка исполнителя в активном спринте |
| `/sm-deliver` | сверка: что в ПЛАНе есть, а в трекере нет (и наоборот) |

## Правила использования

1. **Источник называть.** Факт из трекера — это факт с источником: в артефакте
   пишем ключ задачи (`SPRINT-128`), а не «по данным JIRA».
2. **Не достраивать.** Чего инструмент не вернул — того нет: пустое поле остаётся
   `TBD` или `[УТОЧНИТЬ у {кого}]`, выдумывать оценку, исполнителя или статус
   нельзя (принцип нулевого допуска к галлюцинациям).
3. **Трекер не отменяет консенсус.** Данные из JIRA — вход планирования, а не
   утверждённый план. Гейт консенсуса (`/sm-consensus`) остаётся на месте.
4. **Записи нет.** Коннектор только читает. Заведение задач, смена статусов и
   комментарии — за границей среза; предлагать их как выполненное действие нельзя.
5. **Не настроен — так и сказать.** Инструмент ответил «коннектор не настроен» —
   это сообщение PO («заполните Настройки → Плагины → Управление спринтами»), а
   не повод заполнить план по памяти.
