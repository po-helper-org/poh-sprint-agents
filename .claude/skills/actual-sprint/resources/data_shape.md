# Форма данных: почему она такая

Поля и типы описаны в `contract/team.schema.json` — он источник истины, и его проверяет runner. Здесь только объяснения, которых в схеме не выразить: почему поле существует и почему оно именно такой формы. Полный образец — `examples/example_team.json`.

`resources/report_template.html` получает массив `TEAMS` — по объекту на команду; таблица рендерится из поля `epics` активной команды. Единица отчёта — **эпик**, не история: PO трекает прогресс на уровне эпика, история — деталь внутри эпика.

## Псевдо-эпик «Без эпика»
Истории без эпик-линка не выбрасываем: потерянная работа хуже некрасивой строки. Они собираются в один элемент с `epicKey: null`, `epicTitle: "Без эпика"`, `rowId: "no-epic"` — ровно один такой на команду (инвариант 2).

## Группировка — только визуальная
Никакой агрегированной метрики (% выполнено, «3 из 5») в строке эпика нет и быть не должно: PO просил визуальную группировку, а не сводный статус. Поэтому в объекте эпика нет полей прогресса — счётчики шаблон считает сам из статусов.

## Статусы, бакеты и statusMap
В данных лежат сырые `status` (status.name) и `category` (statusCategory.name) — как вернул трекер. Раскладку в шесть бакетов (`Открыто / Заблокировано / В работе / Тестирование / Ревью / Готово`) делает сборщик команды и кладёт в `statusMap`: у команд разные workflow, и правило «что такое ревью» принадлежит команде, а не шаблону.

Шаблон берёт бакет из `statusMap[status]`, а если карты нет (старый файл данных) — падает в `classifyBucket`. Правила по умолчанию лежат данными в `contract/status_rules.json`, их реализация — `contract/buckets.py`; описание и ловушки — `status_mapping.md`.

Одна раскладка на команду нужна ещё и затем, чтобы разбивка `velocity.split` и счётчики в таблице не могли разойтись: и то и другое считается из одной карты.

## Возраст статуса
`statusChanged` — ISO-дата последней смены статуса из changelog. Дни заранее не считаются: `statusAge`/`ageHtml` в шаблоне вычисляют их от текущей даты в браузере, поэтому открытый через неделю отчёт показывает актуальные цифры, а не замороженные на момент генерации. Порог «просрочки» — константа `STALE_DAYS` (сейчас 3 дня).

`fields.updated` для этого не годится: он двигается от любой правки, включая смену описания.

## Исполнитель
`assignee` — полное ФИО из `displayName`, как вернул трекер. Инициалы считает шаблон (`whoHtml`), в данных их дублировать не нужно. Не назначен → `null`, рендерится как «—».

## Приоритет
`priority` у истории и подзадачи, `epicPriority` у эпика — `priority.name`, как вернул трекер («Высокий», «Critical»). Не заполнен или поле выключено в схеме проекта → `null`. Уровень (`⇈ ↑ = ↓ ⇊`) шаблон выводит из имени сам (`prioHtml`), как бакет из статуса: у инстансов разные наборы приоритетов, и чисел в данных нет. Поля необязательные: свой сборщик может их не отдавать, страница покажет `·`.

## Весь эпик
`epic.scope` — все задачи эпика без подзадач, не только спринт: один пакетный поиск по полю связи с эпиком на пачку эпиков (`params.epic_batch`), порядок — ранг доски. У задачи: ключ, название, тип, статус и категория, исполнитель, приоритет, `sprint` — имя спринта отчёта, в котором задача была (`null` — вне спринтов отчёта: бэклог или давнее), `inSprint` — она в текущем спринте, и подзадачи из заглушек полей (без исполнителя и даты статуса; у задач текущего спринта страница берёт подзадачи из `stories`). Статусы объёма тоже попадают в `statusMap`. Поле необязательное: нет его — нет и кнопки «Смотреть весь эпик». Выключить — `params.epic_scope = false`, потолок — `params.epic_scope_max` (2000).

## Заметки — не данные
Заметки человека живут в `localStorage` браузера (`actual-sprint:{slug}:comments:{спринт}`) и в данные отчёта не попадают: это не факт трекера. У заметки есть `target` — снимок сущности на момент записи (`kind`: `epic` / `story` / `subtask` / `event` / `ref` / `general`, ключ, название, эпик, приоритет, статус, исполнитель). Наружу заметки уходят промтом для ИИ из корзины.

`notes` — наследие прошлой версии страницы: `{ "<rowId>": "текст", "__metrics__": "…", "__logs__": "…" }` из `sprint-report-notes.json`, если файл остался рядом. Runner по-прежнему подставляет его, а страница при первом открытии переносит эти заметки в корзину с пометкой «из заметки». Сборщик `notes` не заполняет.

## Выработка участников (`output`)
`output` — `{ unit, field, sprints: [{ name, current, members: [{ name, split }] }], lead: { имя → { median, count } } }` для операционного слайда презентации. `split` — бакет → `[задач, SP]`: где лежала работа участника **на конец спринта** (у текущего — на сейчас), `done` — его выработка, остальное — застрявшее. Статус и исполнитель на конец спринта восстанавливаются из changelog, а не берутся текущими: закрытая через день после конца спринта задача — не выработка этого спринта. Подзадачи не считаются: оценка в Story Points живёт на задаче. Поле SP ищется по имени (`params.sp_names`) или задаётся `params.sp_field`; не нашлось — `unit: "задач"`, `field: null`, SP нули и предупреждение. `lead` — медиана Lead Time закрытых участником задач за спринты отчёта. Поле необязательное: свои сборщики без него — слайд без выработки участников.

## Инсайды — интерпретация, не данные
`insights` — `{ generatedAt, author, observations: [{ level, text, action?, keys?, about? }], interpretation?, business?, stale? }`. `interpretation` — `{ dynamics[], attention[], recommendations[] }`: интерпретация динамики команды по отдельному промту `sprint-insights/prompts/interpretation.md`, сайдбар по «!» в шапке. `observations` — 3–8 наблюдений для PO по важности, страница выводит их разделом «Инсайды ИИ» внизу сводного отчёта. `business` — `{ objectives{OBJ → название}, streams{эпик → obj, kr, promise, shown, verdict}, rows{история → done, next, blocker}, changes[], demo[], risks[], goalsSource }` для презентации «ФАКТ | спринт»: цели и KR, Sprint Goal, текст строк, изменения, демо, квартальные риски. Пишет их ИИ-агент навыком `/sprint-insights` в `reports/sprint-insights.json` (форма — `contract/insights.schema.json`), runner подставляет при `run`, `merge` и `render`. Подставляет только тогда, когда `dataHash` записи совпал с хешем данных команды (`build.team_digest`: всё, кроме `notes` и `insights`), — наблюдения прошлого сбора рядом со свежими цифрами вводили бы в заблуждение. Исключение — `interpretation`: при несовпавшем хеше runner кладёт только её, с `stale: true` и пустыми наблюдениями, чтобы взгляд на динамику команды не терялся до новой генерации. Сборщик `insights` не заполняет; цифры отчёта от этого поля не зависят.

## Диаграммы управления: две выборки
`control.stories` и `control.subtasks` — независимые наборы одинаковой формы. Разделены потому, что у подзадач свой масштаб Cycle Time: в общей куче он теряется. `points[]` — закрытые за окно, с `cycle` и `outlier`; `risks[]` — незакрытые, идущие дольше медианы своей выборки.

## `_meta`: паспорт сбора
Обязательное поле. Без него не видно, чем и когда собраны цифры, а значит им нельзя доверять (БТ-4): `collectedAt`, `collector@version`, `sha` (её дописывает runner), число запросов, `warnings`. На HTML-странице подвала с паспортом нет — читателю отчёта он ценности не несёт; паспорт печатает runner в сводке, его показывает подвал PDF `/sprint-status` (свежесть данных), по нему `/sprint-insights` считает хеш данных.

## Кнопка «Статус» (одна на эпик) → единая панель из двух колонок
Клик выезжает одна панель с общей шапкой и одной кнопкой закрытия; внутри — две колонки: «Прогресс» (заметка эпика, ключ `actual-sprint:{REPORT_ID}:note:{rowId}`) и «Истории» (список историй с разворотом подзадач). Закрытие — крестик, клик по оверлею или Esc.

## Ловушка вёрстки (не повторять)
Класс ячейки-счётчика (`td.tally`) и класс внутреннего бокса (`.tally-box`) должны отличаться. Одинаковое имя приводило к тому, что правило `display: inline-block` применялось и к `<td>` — ячейка выпадала из табличной раскладки, схлопывалась по ширине и рисовала свою нижнюю границу выше строки.
