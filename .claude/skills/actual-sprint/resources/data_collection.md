# Алгоритм сбора: документация для авторов сборщиков

**Это не инструкция для модели в `/actual-sprint`.** В отчёте данные собирает только сборщик; модель его запускает, а не подменяет. Этот файл нужен, когда ты **пишешь или чинишь сборщик** (`/collector-new`, `/collector-validate`): здесь то, что базовый `templates/python/collector.py` уже делает, и те ловушки JIRA, из-за которых он делает это именно так.

Контракт запуска — `contract/PROTOCOL.md`. Форма выхода — `contract/team.schema.json`. Что означает каждое число — `metrics.md`.

## 0. Доска
Доску по названию команды искать бесполезно, если она названа по техлиду или продукту: в крупном проекте десятки досок. Надёжный способ найти доску конкретного человека — JQL `project = X AND (assignee = <login> OR reporter = <login>) AND updated >= -30d` с полем спринта: в `customfield_10100` лежит `rapidViewId` доски. Это работа человека или `/sprint-setup` — в конфиг попадает готовый `board`.

Список досок (`GET /rest/agile/1.0/board`) нужен сборщику только за именем доски для шапки.

## 1. Спринты
- `GET /rest/agile/1.0/board/{boardId}/sprint?state=closed,active`, **с пагинацией**: у досок с длинной историей первая страница отдаёт самые старые спринты, и активный в выборку не попадает.
- Отфильтровать по `originBoardId == boardId`: в ответ попадают спринты чужих досок.
- Якорь отчёта — активный спринт. Последние N спринтов отсчитываются **от него**, а не от конца списка: иначе в метрики уедут будущие спринты.

## 2. Задачи спринта
- `GET /rest/agile/1.0/sprint/{sprintId}/issue?fields=…&expand=changelog&maxResults=200`, страницами по `total`.
- Один запрос на спринт вместо запроса на задачу (НФТ-6). Список спринта включает и подзадачи — значит даты и исполнители подзадач берутся оттуда же.
- Истории — это задачи, чей `issuetype.name` входит в `params.story_types`. Остальные (задачи, баги) в таблицу эпиков не идут, но в метрики и диаграммы идут.

## 3. Эпик истории
- Точный customfield эпик-линка узнаётся один раз: `GET /rest/api/2/field`, поле с именем «Ссылка на эпик» / «Epic Link» (не «Эпики ЦК/ЦП» и не «Цвет эпика»). ID различается между инстансами — не угадывать. Если автопоиск не сработал, поле задаётся в `params.epic_link_field`.
- Ключ эпика приходит прямо в полях истории, если запросить это поле вместе с остальными. Названия эпиков добираются **одним** запросом: `GET /rest/api/2/search?jql=key in (…)&fields=summary`.
- Истории без эпика собираются в псевдо-эпик `rowId: "no-epic"`, `epicKey: null` — не выбрасываются.
- Группировка строго визуальная: агрегированный процент по эпику не считается.

## 4. Дата последней смены статуса
- Отдельного поля на инстансе нет (`statusCategoryChangedDate` отсутствует) — источник только changelog: максимальный `histories[].created` среди записей с `field == "status"`.
- Статус никогда не менялся → `fields.created`. `fields.updated` не подходит: он двигается от любой правки (комментарий, вложение, смена исполнителя) и завышает свежесть.
- В данные идёт ISO-строка как есть; дни считает браузер.

## 5. Lead / Cycle Time
- По changelog: `lead` = от создания до перехода в категорию «Выполнено», `cycle` = от первого перехода в «В работе» до закрытия.
- Переоткрытие сбрасывает дату закрытия: задача, ушедшая из «Выполнено», больше не закрыта.
- Категории берутся по **id** статуса из `GET /rest/api/2/status`, а не по имени: в changelog имена приходят на языке workflow (`Closed`, `In progress`), а `/status` отдаёт русские.

## 6. Графики сводного отчёта
- **Burndown** — по дням активного спринта. Объём на каждый день пересчитывается из changelog поля `Sprint`: `fromString`/`toString` содержат имена спринтов, по ним видно, когда задача вошла и когда её вынесли. Дни позже `now` помечаются `future: true`.
- **Control** — две независимые выборки (истории и подзадачи): закрытые за окно с Cycle Time и флагом выброса (`cycle > mean + σ`), плюс `risks[]` — незакрытые, идущие дольше медианы своей выборки. Дедуп по ключу: одна задача может числиться в нескольких спринтах.
- **Velocity** — по спринту: сколько в объёме, сколько сделано, и разбивка объёма по бакетам. Разбивка считается из той же `statusMap`, что уходит в данные, — иначе таблица и график разойдутся.
- **Logs** — активность за окно: смены статусов (changelog), комментарии и создание задач. Комментарии и создатель требуют **второго** пакетного прохода с `fields=key,summary,issuetype,created,creator,comment`: в ответе с `expand=changelog` их нет. Дедуп: `st:{history.id}:{key}`, `cm:{comment.id}`, `cr:{key}`.

## 7. Подзадачи
Поле `subtasks` истории уже приходит вложенным списком (`key`, `fields.summary`, `fields.status.name`, `fields.status.statusCategory.name`) — отдельного запроса на каждую не нужно. Пустой список — нормальный случай.

## Ловушки
- **Без VPN** корпоративный хост резолвится в публичный адрес, и все запросы висят до таймаута. Сборщик обязан отдать код `3` и внятное «проверьте VPN/токен», а не молчать двести секунд.
- **Проверку TLS не отключать.** Корпоративный CA подключается через `jira.caBundle` из запроса. По этому соединению идёт личный токен.
- **Только GET.** Ни одного запроса, меняющего состояние трекера, ни в одном режиме.
- **Категория статуса** — основа цвета бейджа, но не заменяет раскладку по бакетам: статусов с одной категорией много и означают они разное («Ожидает тестирование» — это очередь, а не тесты). Правила — `status_mapping.md`, данными в `contract/status_rules.json`.
- **Время только из `now`.** Системные часы делают прогон невоспроизводимым: burndown, окна активности и зона риска зависят от момента запуска.
