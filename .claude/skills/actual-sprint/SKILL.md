# Навык: Actual Sprint — HTML-отчёт по факту спринта

## Роль
Ты — репортёр по факту спринта. Данные отчёта собирают **детерминированные сборщики**, а не ты: твоя работа — запустить runner, показать сводку и объяснить ошибку, если она случилась. Единица отчёта — **эпик**, не история: PO трекает прогресс на уровне эпика.

## Принцип: ИИ не источник данных
Ни одно число на странице не получено моделью напрямую из JIRA. Ты не ходишь в Atlassian MCP, не выполняешь запросы к трекеру и не «дополняешь» собранное по памяти. Между тобой и данными — контракт:

- `contract/team.schema.json` — форма объекта команды;
- `contract/PROTOCOL.md` — как запускается сборщик и что он отдаёт;
- `runner/run.py` — единственный способ получить данные и собрать страницу.

Если сборщика нет, он не проверен или JIRA недоступна — отчёт не собирается. Это не повод собрать данные самому: это повод назвать следующий шаг человеку.

Писать и починять код сборщика — можно и нужно (`/collector-new`, `/collector-validate`). Собирать данные вместо сборщика — нельзя.

## Стадии

### 1. Запустить runner
```bash
python3 .claude/skills/actual-sprint/runner/run.py run --config sprint-report.config.toml
```
Одна команда на все команды конфига. Фильтр по команде — `--only team-a`. Конфига нет → это `/sprint-setup`, а не повод угадывать доски.

### 2. Показать сводку (то, что напечатал runner)
По каждой команде: доска, спринт, эпиков, закрыто/всего, событий, запросов, время. Плюс строка итога: схема, инварианты, предупреждения, сколько заметок подхвачено, и путь к файлу. Ничего не додумывай: показываешь ровно то, что вышло из runner.

Предупреждения сборщика (новый статус вне правил бакетов, истории без эпика) проговори человеку — это сигналы, что workflow команды поехал.

### 3. STOP
Дальше решает человек. Не открывай файл, не публикуй как Artifact, не предлагай автозапуск.

## Когда runner отказал

Первым делом — `python3 .claude/skills/actual-sprint/runner/run.py doctor`: он проверяет стенд локально, без похода в JIRA (файлы плагина, конфиг, переменные окружения, CA-бандл, статус проверки по каждой команде). Разбор реальных отказов по шагам — `docs/actual-sprint-debug.md`.

| Что в выводе | Что это значит | Что говоришь |
|---|---|---|
| `сборщик не проверен` / `изменён после проверки` | strict-режим: код сборщика не сверялся с JIRA | «Запустите `/collector-validate <slug>`» |
| `JIRA недоступна` (код 3) | нет сети, VPN или токен просрочен | «Проверьте VPN и `JIRA_PERSONAL_TOKEN`». Обходных путей не предлагаешь |
| `схема ✗` / `инвариант N` | сборщик отдал не то, что обещал | Поправить код сборщика: `/collector-validate <slug>` |
| `конфиг: …` | ошибка в `sprint-report.config.toml` | Назвать команду и поле из сообщения |
| `сертификат JIRA не проверился` | корпоративный CA не подключён | «Укажите путь к бандлу в `jira.ca_bundle`». Проверку TLS не отключаем |

HTML при любой из этих ошибок не пишется, прошлый файл остаётся нетронутым — так на странице никогда не окажется половины правды.

## Что где лежит
```
contract/      team.schema.json · PROTOCOL.md · status_rules.json · buckets.py
runner/        run.py (run | validate | lock | new) · validate.py · build.py · schema.py
templates/     python/collector.py — базовый сборщик, все правила в params
resources/     report_template.html · metrics.md · status_mapping.md · data_shape.md · data_collection.md
examples/      example_team.json · sprint-report.config.toml
```

Проект пользователя: `sprint-report.config.toml` (правит человек), `sprint-report.lock.json` (пишет только runner), `collectors/<slug>/` (свои сборщики), `reports/`.

## Команды
- `/sprint-setup` — собрать конфиг по вопросам: JIRA, команды, доски.
- `/collector-new <slug>` — свой сборщик из шаблона, когда `params` базового не хватает.
- `/collector-validate <slug>` — схема, инварианты, сверка выборки с JIRA, запись хеша.
- `/actual-sprint [команда]` — собрать отчёт.

## Дизайн-контракт HTML (не менять произвольно)
- Ч/б интерфейс, цвет несёт смысл только в статусах. Hero сверху с полосой-разделителем; название доски в hero — ссылка на саму доску в JIRA.
- В hero вместо счётчика эпиков — **Lead Time за 3 спринта в формате `среднее / медиана / кол-во`**. Это кликабельный элемент: открывает панель со сводным отчётом команды за 3 спринта — три графика без таблиц: burndown текущего спринта, производительность «запланировано / сделано» с разбивкой планового столбца по статусам, диаграмма управления со списком задач-выбросов (см. `resources/metrics.md`). Сводные числа не дублировать таблицами: Lead Time уже в шапке, остальное читается из подписей под графиками. Подписи колонок панели переключаются на «Заметка» / «Метрики», заметка сводного отчёта хранится под отдельным ключом `__metrics__`.
- Таблица: одна строка = один эпик, **без шапки-заголовка** (названия колонок не несут информации — эпик и так виден, счётчики расшифровываются подсказкой). Колонки: «Эпик» (простой текст, БЕЗ ссылки — иначе клик по строке конфликтует с переходом; ссылка на JIRA живёт в шапке панели) | счётчики статусов | кнопка действия.
- **Кликабельна вся строка**, не только кнопка «Статус»: обработчик вешается на `<tr>`, курсор `pointer`, подсветка строки по hover. Кнопка остаётся как явная точка входа и как носитель маркера заметки.
- **Счётчики статусов** — миниатюрный цветной текст `2/2/3/0/5/1` в порядке `Открыто / Заблокировано / В работе / Тестирование / Ревью / Готово`. Агрегируется ВСЯ иерархия эпика: каждая История + каждая её Подзадача = единица подсчёта. Ни легенды, ни подписей колонок — расшифровка во всплывающей подсказке при наведении, только ненулевые бакеты словами. Цвета бакетов и маппинг статусов — `resources/status_mapping.md`; реализация — `classifyBucket` в шаблоне (считается в браузере при рендере, в данных бакеты не хранятся).
- Проценты/сводный статус эпика не выводить — только счётчики и группировка.
- Кнопка **«Статус»** (одна на эпик) → выезжает ОДНА неделимая панель справа: общая рамка, общая тень, **одна** кнопка закрытия. Общая шапка (ключ эпика, название, ссылка «Открыть в JIRA →») — не дублировать её по колонкам. Внутри шапки — две колонки, разделённые тонкой линией **без тени между ними**:
  1. **Колонка «Прогресс»** (слева, фиксированная ширина) — обычный `<textarea>`, plain-текст, автосохранение в `localStorage` по ключу `actual-sprint:{REPORT_ID}:note:{rowId}` эпика (`REPORT_ID` — уникальный на файл отчёта, чтобы несколько открытых отчётов не путали заметки в одном браузере). Кнопка «Статус» получает класс `has-note` (визуальная точка-маркер), если заметка не пуста.
  2. **Колонка «Истории»** (справа, тянется) — сразу список историй эпика (`key — title` + цветной статус-бейдж + возраст статуса), без сводных чипов сверху: счётчики уже есть в таблице, дублировать их в панели не нужно. У истории с подзадачами — стрелка-тоггл разворачивает их список под ней (тот же набор: бейдж + возраст, вложенно). Нет историй в эпике → «Историй нет.». Панель широкая (~1040px), чтобы длинные названия историй не рвались на четыре строки.
- **Возраст статуса** — короткая метка справа от бейджа: «1д», «22д». Дольше `STALE_DAYS` (3 дня) без смены статуса — красным. Считается в браузере от `statusChanged`, не зашивается числом при генерации.
- **Готовые задачи никогда не красные**: у бакета `done` возраст всегда зелёный, сколько бы дней ни прошло — закрытая задача стоит без движения по определению, «просрочка» там ложный сигнал. Подсказка меняется на «Закрыто N дн. назад».
- **Исполнитель** — двухбуквенные инициалы слева от ключа задачи (фамилия + имя из `displayName`: «Фамилия Имя Отчество» → «ФИ»), полное ФИО во всплывающей подсказке. Не назначен → «—» приглушённым. Колонка фиксированной ширины, чтобы названия задач выстраивались в ровную колонку.
  Закрытие — крестик, клик по оверлею, Esc.
- Кнопка **«Logs»** в правом верхнем углу страницы → та же панель в режиме ленты: что команда делала за последнюю неделю — смены статусов, комментарии и создание задач. Фильтры по типу события и по автору комбинируются, группировка по дням. Заметка этой панели хранится под отдельным ключом `__logs__`.
- Все внешние ссылки — `target="_blank" rel="noopener"`.

## Границы
Только чтение JIRA + генерация локального HTML-файла. Никаких записей в JIRA/Confluence, никакого автопубликования как Artifact без явной просьбы, никакого cron/автозапуска.
