# Навык: Actual Sprint — HTML-отчёт по факту спринта

## Роль
Ты — репортёр по факту спринта. Данные отчёта собирают **детерминированные сборщики**, а не ты: твоя работа — запустить runner, показать сводку и объяснить ошибку, если она случилась. Единица отчёта — **эпик**, не история: PO трекает прогресс на уровне эпика.

## Принцип: ИИ не источник данных
Ни одно число на странице не получено моделью напрямую из JIRA. Ты не ходишь в Atlassian MCP, не выполняешь запросы к трекеру и не «дополняешь» собранное по памяти. Между тобой и данными — контракт:

- `contract/team.schema.json` — форма объекта команды;
- `contract/PROTOCOL.md` — как запускается сборщик и что он отдаёт;
- `runner/run.py` — единственный способ получить данные и собрать страницу.

Если сборщика нет, он не проверен или JIRA недоступна — отчёт не собирается. Это не повод собрать данные самому: это повод назвать следующий шаг человеку.

Писать и починять код сборщика — можно и нужно (`/collector-new`, `/collector-validate`). Собирать данные вместо сборщика — нельзя.

## Стадии

### 1. Запустить runner
```bash
python3 .claude/skills/actual-sprint/runner/run.py run --config sprint-report.config.toml
```
Одна команда на все команды конфига. Фильтр по команде — `--only team-a`. Конфига нет → это `/sprint-setup`, а не повод угадывать доски.

### 2. Показать сводку (то, что напечатал runner)
По каждой команде: доска, спринт, эпиков, закрыто/всего, событий, запросов, время. Плюс строка итога: схема, инварианты, предупреждения, сколько заметок подхвачено, и путь к файлу. Ничего не додумывай: показываешь ровно то, что вышло из runner.

Предупреждения сборщика (новый статус вне правил бакетов, истории без эпика) проговори человеку — это сигналы, что workflow команды поехал.

### 3. Интерпретация ИИ — сразу, в той же генерации
Сбор прошёл (код 0) — не останавливайся: интерпретация пишется на этапе генерации отчёта, иначе её потеряют. Это второй конвейер — навык `sprint-insights`, с отдельным промтом для интерпретации `sprint-insights/prompts/interpretation.md`:

```bash
python3 .claude/skills/sprint-insights/insights.py facts        # факты из только что записанного снимка
# → reports/sprint-insights.json: observations и interpretation (по промту interpretation.md)
python3 .claude/skills/sprint-insights/insights.py apply        # проверка, архив, пересборка страницы
```

С `--team <slug>`, если сбор был `--only`. `apply` пересобирает страницу из снимка без JIRA: цифры не меняются, добавляются раздел «Инсайды ИИ» и сайдбар «!» в шапке. Бизнес-отчёт здесь не генерируется — это отдельный навык `/sprint-business`. Принятый файл ложится в `reports/insights-archive/` — по нему следующий сбор увидит прошлую интерпретацию (`previousInterpretation` в фактах). Есть `✗` — поправь файл и повтори `apply`; сбор не перезапускай. Сбор упал — этот шаг не делай: интерпретировать нечего.

### 4. STOP
Дальше решает человек. Не открывай файл, не публикуй как Artifact, не предлагай автозапуск.

## Когда runner отказал

Первым делом — `python3 .claude/skills/actual-sprint/runner/run.py doctor`: он проверяет стенд локально, без похода в JIRA (файлы плагина, конфиг, переменные окружения, CA-бандл, статус проверки по каждой команде). Разбор реальных отказов по шагам — `docs/actual-sprint-debug.md`.

| Что в выводе | Что это значит | Что говоришь |
|---|---|---|
| `сборщик не проверен` / `изменён после проверки` | strict-режим: код сборщика не сверялся с JIRA | «Запустите `/collector-validate <slug>`» |
| `JIRA недоступна` (код 3) | нет сети, VPN или токен просрочен | «Проверьте VPN и `JIRA_PERSONAL_TOKEN`». Обходных путей не предлагаешь |
| `схема ✗` / `инвариант N` | сборщик отдал не то, что обещал | Поправить код сборщика: `/collector-validate <slug>` |
| `конфиг: …` | ошибка в `sprint-report.config.toml` | Назвать команду и поле из сообщения |
| `сертификат JIRA не проверился` | корпоративный CA не подключён | «Укажите путь к бандлу в `jira.ca_bundle`». Проверку TLS не отключаем |

HTML при любой из этих ошибок не пишется, прошлый файл остаётся нетронутым — так на странице никогда не окажется половины правды.

## Что где лежит
```
contract/      team.schema.json · insights.schema.json · PROTOCOL.md · status_rules.json · buckets.py
runner/        run.py (run | merge | render | validate | lock | new | doctor) — пишут отчёт PO и снимок данных · validate.py · build.py · schema.py · mini_toml.py
templates/     python/collector.py — базовый сборщик, все правила в params
resources/     report_template.html · shared/ (движок, общий с бизнес-отчётом sprint-business) · metrics.md · status_mapping.md · data_shape.md · data_collection.md
examples/      example_team.json · sprint-report.config.toml
```

Проект пользователя: `sprint-report.config.toml` (правит человек), `sprint-report.lock.json` (пишет только runner), `collectors/<slug>/` (свои сборщики), `reports/` — страница и снимок данных `sprint-report.data.json`, из которого `/sprint-status` собирает PDF для чата, а `/sprint-insights` — факты для интерпретации графиков; `sprint-insights.json` — сама интерпретация от ИИ (пишет агент, runner только встраивает).

## Команды
- `/sprint-setup` — собрать конфиг по вопросам: JIRA, команды, доски.
- `/collector-new <slug>` — свой сборщик из шаблона, когда `params` базового не хватает.
- `/collector-validate <slug>` — схема, инварианты, сверка выборки с JIRA, запись хеша.
- `/actual-sprint [команда]` — собрать отчёт и сразу записать интерпретацию ИИ (стадия 3).
- `/sprint-insights [команда]` — отдельный конвейер: ИИ-агент интерпретирует графики сводного отчёта по фактам из снимка; `run.py render` пересобирает страницу без JIRA. Инсайды привязаны к хешу данных: после нового сбора старые на страницу не попадают.
- `/sprint-business [команды]` — бизнес-отчёт «ФАКТ | спринт» для комитета: отдельный навык и файл `reports/sprint-business.html` на тех же данных (снимок этого runner'а). На странице отчёта PO — кнопка «Бизнес-отчёт» с промтом на него.

## Дизайн-контракт HTML (не менять произвольно)
- Ч/б интерфейс, цвет несёт смысл только в статусах. Hero сверху с полосой-разделителем; название доски в hero — ссылка на саму доску в JIRA.
- **«!» рядом с названием команды** — интерпретация ИИ (`team.insights.interpretation`, отдельный промт `sprint-insights/prompts/interpretation.md`, пишется при генерации отчёта). Клик — сайдбар из трёх разделов: «Что можно сказать о динамике команды», «На что стоит обратить внимание», «Рекомендации на будущее»; ключи задач — ссылками в JIRA; внизу «Интерпретация ИИ, не данные · автор · время»; правый клик по пункту — заметка. Кнопка чёрная — интерпретация есть; пунктир — написана по прошлому сбору (данные пересобраны, в сайдбаре плашка «Написано по прошлому сбору»); серая — нет, сайдбар объясняет, откуда она берётся. Устаревшая интерпретация не теряется до новой — в отличие от наблюдений и бизнес-блока, привязанных к цифрам.
- В hero вместо счётчика эпиков — **Lead Time за 3 спринта в формате `среднее / медиана / кол-во`**. Это кликабельный элемент: открывает панель со сводным отчётом команды за 3 спринта — три графика без таблиц: burndown текущего спринта, производительность «запланировано / сделано» с разбивкой планового столбца по статусам, диаграмма управления со списком задач-выбросов (см. `resources/metrics.md`). Сводные числа не дублировать таблицами: Lead Time уже в шапке, остальное читается из подписей под графиками. Подпись панели — «Метрики».
  - Под графиком — только легенда и одна строка итога; расшифровка («Как читать») — в подсказке иконки **«i»** у заголовка (hover/focus, на телефоне — тап; открывается туда, где есть место). Там же статистика окна диаграммы управления. Интерпретации в подсказке нет.
  - **«Инсайды ИИ»** — последний раздел сводного отчёта: «На что обратить внимание PO: состояние команды в этом спринте и тенденция». Наблюдения из `team.insights.observations` по порядку агента (первое — главное): точка и метка уровня (нужна реакция / присмотреться / работает / наблюдение), метка «о чём» (спринт, команда, график), текст, действие `→ …` приглушённым, ключи задач — ссылками в JIRA; внизу «Интерпретация ИИ, не данные · автор · время». Правый клик — заметка к наблюдению (`kind: insight`). Наблюдений для этого сбора нет — раздел всё равно на месте: «ИИ-агент ещё не смотрел этот сбор. Попросите его: /sprint-insights».
  - Списки «Выбиваются из коридора» и «В зоне риска» — сетка из трёх фиксированных колонок: название (в одну строку, ключ приглушён) | статус-бейдж | дни справа, табличными цифрами. Правый клик по строке — заметка к задаче, по графику — заметка к графику (`kind: chart`).
- Таблица: одна строка = один эпик, **без шапки-заголовка** (названия колонок не несут информации — эпик и так виден, счётчики расшифровываются подсказкой). Колонки: «Эпик» (простой текст, БЕЗ ссылки — иначе клик по строке конфликтует с переходом; ссылка на JIRA живёт в шапке панели) | счётчики статусов | кнопка действия.
- **Кликабельна вся строка**, не только кнопка «Статус»: обработчик вешается на `<tr>`, курсор `pointer`, подсветка строки по hover. Кнопка остаётся как явная точка входа и как носитель маркера комментариев (точка, если по эпику или его задачам есть комментарии).
- **Счётчики статусов** — миниатюрный цветной текст `2/2/3/0/5/1` в порядке `Открыто / Заблокировано / В работе / Тестирование / Ревью / Готово`. Агрегируется ВСЯ иерархия эпика: каждая История + каждая её Подзадача = единица подсчёта. Ни легенды, ни подписей колонок — расшифровка во всплывающей подсказке при наведении, только ненулевые бакеты словами. Цвета бакетов и маппинг статусов — `resources/status_mapping.md`; реализация — `classifyBucket` в шаблоне (считается в браузере при рендере, в данных бакеты не хранятся).
- Проценты/сводный статус эпика не выводить — только счётчики и группировка.
- Кнопка **«Статус»** (одна на эпик) → выезжает ОДНА неделимая панель справа (~860px): общая рамка, общая тень, **одна** кнопка закрытия. Общая шапка: ключ эпика — сам ссылка в JIRA (иконка внешней ссылки справа, подсказка «Открыть в JIRA»; отдельной кнопки нет), ниже название. Внутри одна колонка: сверху комментарии по эпику и его задачам (только чтение, если есть), ниже подпись «Истории» и список историй (`приоритет · инициалы · key — title` + цветной статус-бейдж + возраст статуса), без сводных чипов: счётчики уже есть в таблице. У истории с подзадачами — стрелка-тоггл разворачивает их список (тот же набор, вложенно). Нет историй → «Историй нет.». Большой textarea-заметки в панели **нет**.
- **«Смотреть весь эпик»** — кнопка в шапке панели под названием, только у эпика с полем `scope`. Переключает тот же сайдбар на полный объём эпика, не только спринт: сверху «Сделано X из Y · N%» и полоса статусов, ниже разделы **«Осталось»** (сгруппировано по процессу: заблокировано → в работе → тестирование → ревью → открыто) и **«Сделано»**. Строка — как у истории спринта (приоритет, инициалы, ключ и название, статус, разворот подзадач), справа вместо возраста метка: «в спринте» / имя прошлого спринта / «вне спринта». Заголовки разделов липкие и сворачиваются по клику, подгруппы «Осталось» по процессу — тоже. При открытии всё свёрнуто: видны итог и заголовки со счётчиками, задачи — по клику: список бывает длинным. Правый клик по строке — заметка. Кнопка меняется на «← Задачи спринта».
- **Заметки — корзина справа вверху** (приём страницы ревью БФТ, вид — панели poh-okr-plugin). Рядом с «Logs» — кнопка «Комментарии (N)»; по клику под ней панель со скруглённой карточкой заметок. Лога над таблицей и textarea в панели эпика нет.
  - **Заметка** — короткий текст строкой; если привязана — под ним мелко `ключ · название`. Справа две иконки 28×28 с контуром 1.4px — **карандаш** (редактировать) и **мусорка** (удалить); серые, появляются при наведении на строку, на hover — мягкий фон. Время создания и правки — в подсказке строки, не в интерфейсе.
  - **Правка** — в самой строке: текст и поле «К чему», Enter — сохранить, Esc — отмена. Ключ не меняли — снимок сущности остаётся прежним.
  - **Новая заметка** — поле «Добавить заметку» сверху панели; как только начали писать, под ним появляется «К чему» — ключ эпика или задачи с подсказками из отчёта. Ключ из отчёта раскрывается в снимок сущности (тип, ключ, название, эпик, приоритет, статус, исполнитель на момент записи); ключ не из отчёта сохраняется как «Вне отчёта»; пусто — без привязки. Enter — добавить.
  - **Правый клик** по строке эпика, истории, подзадачи, шапке панели или событию ленты — поле заметки у курсора, уже привязанное к строке; над ним заметки к той же сущности строками с мусоркой. Enter — сохранить, Esc — отмена; рядом кнопки «Отмена» и «Сохранить». На сенсорном экране то же — **долгим нажатием** 0,5 с (Safari на iOS не шлёт contextmenu); отпускание пальца после него не считается тапом.
  - **Промт для ИИ** — кнопка «Скопировать промт для ИИ» внизу панели, иконка-глаз рядом раскрывает сам текст. Промт: контекст (команда, спринт, доска, время данных), формат строки, затем `N. [к чему относится] текст`.
  - Маркеры: точка на кнопке «Статус» у эпика с заметками по нему или его задачам, счётчик у истории и подзадачи.
  - Хранение — `localStorage`, ключ `actual-sprint:{slug}:comments:{sprintName}`: своя корзина у каждой команды и спринта. Заметки прошлых версий (`actual-sprint:{slug}:note:*` и `team.notes` из файла) один раз переезжают в корзину, старые ключи не удаляются.
- **Приоритет** — глиф фиксированной ширины слева: у эпика в таблице, у истории и подзадачи в панели. Уровень выводится из имени (`prioHtml`): `⇈` блокирующий/критический, `↑` высокий, `=` средний, `↓` низкий, `⇊` самый низкий, `·` не задан; имя из JIRA — в подсказке. Ч/б: высокие — насыщенным, средние и низкие — приглушённым; цвет по-прежнему только у статусов.
- **Возраст статуса** — короткая метка справа от бейджа: «1д», «22д». Дольше `STALE_DAYS` (3 дня) без смены статуса — красным. Считается в браузере от `statusChanged`, не зашивается числом при генерации.
- **Готовые задачи никогда не красные**: у бакета `done` возраст всегда зелёный, сколько бы дней ни прошло — закрытая задача стоит без движения по определению, «просрочка» там ложный сигнал. Подсказка меняется на «Закрыто N дн. назад».
- **Исполнитель** — двухбуквенные инициалы слева от ключа задачи (фамилия + имя из `displayName`: «Фамилия Имя Отчество» → «ФИ»), полное ФИО во всплывающей подсказке. Не назначен → «—» приглушённым. Колонка фиксированной ширины, чтобы названия задач выстраивались в ровную колонку.
  Закрытие — крестик, клик по оверлею, Esc.
- Кнопка **«Logs»** в правом верхнем углу страницы → та же панель в режиме ленты: что команда делала за последнюю неделю — смены статусов, комментарии и создание задач. Фильтры по типу события и по автору комбинируются, группировка по дням. Правый клик по событию — комментарий к задаче события.
- Все внешние ссылки — `target="_blank" rel="noopener"`.
- **«Бизнес-отчёт»** — кнопка в правом верхнем углу (рядом с Logs). Колоды на странице нет: бизнес-отчёт «ФАКТ | спринт» — отдельный навык `sprint-business` и отдельный файл `reports/sprint-business.html` на тех же данных. Кнопка открывает окно с готовым промтом «собери бизнес-отчёт»: `/sprint-business`, команды и спринты, снимок данных и время сбора, правило «цели только из OKR/roadmap PO», заметки PO из корзины всех команд. «Скопировать промт» — в буфер; Esc, «Закрыть» или клик мимо — закрыть.
- **Телефон и PWA** (эталон — iPhone 15 Pro, 393 px). В `<head>`: `viewport` с `viewport-fit=cover`, `apple-mobile-web-app-capable`, короткое имя «Спринт», иконка 180×180 PNG встроена `data:`-ссылкой — файл остаётся самодостаточным. До 640 px: строка эпика — карточка (название во всю ширину, счётчики и `›` под ним, точка — есть заметки); вкладки команд в одну строку с прокруткой; панель на весь экран, крестик 44×44 ниже чёлки; статус задачи второй строкой; подсказка «i» — шторкой снизу; поле заметки — сверху (клавиатура). Поля — от `env(safe-area-inset-*)`. Без наведения (`hover: none`): «i» по тапу, иконки корзины видны всегда, поля ввода 16 px (иначе iOS увеличивает страницу). Горизонтальной прокрутки нет ни на одном экране — держит `tests/e2e/report_mobile.mjs`.
- **Подвала с паспортом сбора нет** («собрано …, collector@version, N запросов, предупр.»): читателю отчёта он не нужен. Паспорт остаётся в `_meta` данных — его печатает runner и показывает PDF `/sprint-status`.
